# UAC 成员核实记录

UAC 不按姓名、邮箱或用户填写的员工号匹配团队成员。已有成员可在新近认证的团队会话中完成 UAC 双认证绑定。管理员预先核实员工号时，也可在受保护部署文件中准备以下记录，由 `auriga.org.uac-verifications-file` 指定文件位置；不向浏览器或公开配置接口暴露该文件。

租户已启用并配置 UAC 时，门户（含桌面平台设备登录）的首次登录在企业身份及现有 MFA 策略验证完成后，默认创建普通成员，无需预置名单或邀请。UAC 扫码登录本身即完成认证，不再要求登记验证器或平台 TOTP。新成员不自动获得角色或组，不会并入其他账号。已知停用、离职或绑定冲突的工号不会再入组；只改变既有工号的 ASCII 大小写也不能再注册，现有精确工号仍按原规则识别。明确提供邀请时仍须核实邀请及其对象。仅本机桌面扫码不建团队成员。

自动入组用当前租户、供应商、精确工号保存核实关系，与普通成员在同一个 org 事务写入，事件沿 `auto_provision`。该关系的 `verified_by` 记录经企业服务验证的本人账号 ID；私有文件提供的人工核实记录仍保留核实管理员 ID。IAM 失败后可用原绑定重试，不创建第二个成员。

文件为 JSON 数组，每条都须包含 `tenantId`、`providerId`、`employee`、`verified: true`、`verifiedBy`（核实管理员的内部 UUID）和 `verifiedAt`（UTC 时间）。管理员必须先实际核实员工号，文件本身是受信部署输入，不能用用户表单直接生成。身份主键只去首尾空白，保留前导零及大小写。忽略 ASCII 大小写仅用于 token-verify 响应身份比较，不能用于合并两条成员身份。

既有成员记录另含 `accountId`，且成员必须存在并处于 active 状态。专用邀请记录另含 `invitationId` 和 `purpose: "uac_login"`，邀请必须只允许使用一次；受邀人由验证得到的员工号精确核对，普通团队账号注册不能消费该邀请。不能同时填写 accountId 和 invitationId。部署文件中的员工号/UUID 均由部署方实际填写，不提交仓库。

启动初始化在数据库迁移后导入，重复导入同一关系幂等，冲突、未知成员、多人映射和未来核实时间均拒绝启动。关系写入 org 自己的 FORCE RLS 表，IAM 只通过策略接口读取，不跨 schema 查询。所有副本共享数据库中的关系。移除文件不解除已建立的身份关联；停用/离职沿既有成员管理操作执行。

邀请消费与 org 成员创建同事务；IAM 在登录事务创建时预分配账号 ID。若 org 已消费邀请而 IAM 随后回滚，重试解析已建立的核实关系，使用同一账号 ID 建立 IAM 镜像，不再次消耗邀请。成员名称、类型与活跃状态取 org 权威值，企业资料不能授予角色或权限。
