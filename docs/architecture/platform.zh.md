## 一、设计原则

1. **按业务边界划服务，按部署规模决定合不合并**。服务之间只通过契约（接口 + 事件）交互，不共享表、不互相调内部类。小规模私有部署时，Java 业务服务可以合并到一个进程里跑；规模大了再拆开独立部署。代码不用改。
2. **各取所长的多语言**：业务逻辑用 Java（生态成熟、主流、好招人）；高并发长连接、需要贴近操作系统的部分用 Go；DSH 本身和插件是 Node。语言不同不要紧，契约统一就行。
3. **契约优先**：先写 OpenAPI 和 protobuf，再写代码。多人（或多个 AI 编码助手）并行开发时以契约为准。
4. **从单机到集群用同一套产品**：单机安装包（Windows / Linux）、Docker Compose、Kubernetes 三种交付形态，不为某一种单独维护代码分支。
5. **不强依赖重型中间件**：单机版不需要 Kubernetes、Nacos、Kafka、Redis；所有内置组件都要能在 Windows 上原生运行。
6. **现在就要定、以后很难改的，一次定好**：租户字段、审计、身份令牌格式、服务间鉴权、数据所有权。

## 三、服务划分

| 服务 | 语言 | 负责 | 自己的数据 |
|---|---|---|---|
| **edge** 接入网关 | Go | 唯一对外入口；TLS（可交给外部反代）；按路由分发到各服务；校验会话；限流；把浏览器到 DSH 实例的 HTTP / WebSocket 反代到对应节点并加签名身份头；主站和管理台按源隔离；托管前端静态文件 | 无（路由表从事件和缓存里来） |
| **iam** 身份认证 | Java | 账号；**身份源**（平台核心 + 可插拔连接器：内置团队账号和应急账号、标准协议、微信等预置模板、企业定制连接器，见身份源文档）；会话；设备；API 令牌和服务账号；**OIDC 提供方**（平台各服务和第三方系统单点登录） | `iam` schema |
| **org** 组织与权限 | Java | 租户、成员、组、角色和权限集合、策略、配额、邀请 | `org` |
| **workspace** 工作空间 | Java | 每人实例的规格计算、节点调度、生命周期决策（闲置回收、闹钟唤醒、常驻）、灰度升级、节点管理；向节点代理下发规格 | `workspace` |
| **resource** 资源中心 | Java | 插件、skill、环境模板的上传、审核、签名、版本、可见范围、分发；插件包存对象存储 | `resource` |
| **knowledge** 知识 | Java | 团队知识空间管理、知识沉淀流程、审核策略；底层知识库由 kb-server 提供 | `knowledge` |
| **collab** 协作 | Java | 团队 agent 总线（任务、私信）、通知中心（站内、邮件、IM、Webhook） | `collab` |
| **audit** 审计 | Java | 收集所有服务的审计事件；查询、导出、留存、防篡改 | `audit`（按月分区） |
| **ops** 运维 | Java | 系统设置、备份调度、离职流程、数据导出删除、许可证 | `ops` |
| **ai-gateway** | Go | 模型网关：多供应商、key 托管、流式转发、按人计量和预算。MCP 网关：把平台自己的工具、团队知识库聚合起来，按人鉴权后提供给 DSH 实例；以后打通外部系统时，它们的数据也从这里提供 | `ai`（用量明细） |
| **egress** 出网代理 | Go | 实例出网只能走它；分类白名单由 org 的策略下发 | 无 |
| **agent** 节点代理 | Go | 每台主机一个；按 workspace 下发的规格在本机安装、配置、启停 DSH 实例；实例目录、文件、迁移、备份 | 本地状态文件 |
| **kb-server** | Node | 现有 dsh-memwiki 的远程模式，不重写 | 文件 + git |
| **launcher / ctl** | Go | 单机版的安装、启停、状态、备份、升级、改端口、切换数据库 | — |

**合并部署**：Java 的 8 个服务各自是一个 Maven 模块。另有一个 `platform-app` 启动器，把选中的模块装进同一个 JVM。单机版只跑一个 Java 进程（约 0.6–1 GB 内存）；集群版每个服务独立部署、独立扩容。模块之间的调用都走接口：同进程时是本地调用，分开部署时换成 gRPC 客户端。具体做法：每个服务拆成 `api`（接口和数据结构）和 `impl` 两个 Maven 子模块，别的服务只能依赖 `api`；合并部署和分开部署时 `api` 的实现分别是本地 Bean 和 gRPC 客户端，由启动配置选择。事件在两种部署下都走 NATS，行为一致。这些规则由架构测试（ArchUnit）在 CI 里强制检查。

## 四、技术栈

| 层 | 选择 | 说明 |
|---|---|---|
| 前端 | Vue 3 + TypeScript + Vite + Pinia + Vue Router + Element Plus | 主流组合；视觉沿用用户定的液态玻璃黑蓝风格，用 CSS 变量换主题 |
| DSH 里的团队面板 | Vue 组件编译成 Web Component，由插件加载 | DSH 前端是 React，用 Web Component 不受框架限制；面板跟着平台发版，不用重发插件 |
| 业务服务 | Java 25 LTS + Spring Boot 4.x（开工时取最新稳定版）+ 虚拟线程 | |
| 安全 | Spring Security（含 Authorization Server） | iam 做 OIDC 提供方；其他服务做资源服务器，校验 JWT |
| 持久化 | MyBatis-Plus + Flyway + PostgreSQL JDBC | MyBatis-Plus 是国内主流，自带多租户插件，自动给 SQL 加 `tenant_id` 条件 |
| Go 服务 | Go 最新稳定版；gRPC；标准库 HTTP | 单文件可执行，Windows / Linux / amd64 / arm64 交叉编译 |
| 服务间同步调用 | 对外 REST（OpenAPI 3.1）；对内 gRPC（protobuf） | Java 和 Go 都是一等支持 |
| 服务间异步 | NATS JetStream | 单个约 20 MB 的可执行文件，Windows / Linux 原生运行；同时提供 KV 存储，用来放会话缓存、路由表，省掉 Redis（Redis 没有官方 Windows 版） |
| 可靠事件 | 事务外发表（outbox）：业务数据和待发事件在同一个数据库事务里写入，再由转发器投递到 NATS | 不丢事件、不重复处理（消费方按事件 id 去重） |
| 数据库 | PostgreSQL 17（内置）/ ≥ 15（外置） | 见第七节 |
| 对象存储 | 抽象成接口；单机用本地磁盘，集群用 S3 兼容存储 | 插件包、上传文件、备份 |
| 可观测 | Micrometer / OpenTelemetry、Prometheus 指标、结构化 JSON 日志；Grafana / Loki 可选 | |
| 构建 | Maven 多模块、Go workspace、pnpm workspace | |

**考虑过但没选的**：
- **Keycloak 做身份认证**：功能全，但扫码确认、两位比对码、邀请制、应急账号这些流程都要写 Java SPI 去定制，登录页也只能用 FreeMarker 主题改，定制成本比在 Spring Security 上自己做还高；它本身也很重。
- **Spring Cloud 全家桶（Nacos、Gateway、Sentinel）**：单机版装不下，Windows 上也不好部署。服务发现交给部署环境（单机用固定配置，Compose 用服务名，Kubernetes 用 Service）；网关用 Go 写的 edge，因为它要做反代 DSH 实例这种特殊逻辑。
- **Kafka**：太重。NATS 足够，规模大了以后也能换。

## 五、服务间通信与数据

### 5.1 三种通信

| 场景 | 方式 | 例子 |
|---|---|---|
| 浏览器、外部系统 → 平台 | REST（OpenAPI），经 edge | 管理台、开放 API |
| 服务 → 服务（要马上拿到结果） | gRPC，带服务身份 | workspace 问 org 某人的配额 |
| 服务 → 服务（通知别人发生了什么） | NATS 事件 | `user.disabled` 发出后：workspace 停实例、iam 吊销会话、resource 转交发布者、audit 记录 |
| workspace ↔ 节点代理 | gRPC 双向流，由节点代理主动连 | 下发规格、上报状态 |
| 平台 ↔ DSH 实例 | 实例 → 平台：REST（实例令牌）；平台 → 实例：edge 反代（签名身份头） | 插件上报活动；浏览器访问实例 |

### 5.2 数据归属

- **每个服务只读写自己的 schema**。要别人的数据就调接口，或者订阅事件在本地存一份只读副本。小规模部署时所有 schema 在同一个 PostgreSQL 实例里，规模大了可以分库。
- **所有业务表从第一天起都带 `tenant_id`**。私有部署默认只有一个租户；以后做 SaaS 时一套部署服务多家客户，不用迁移数据。MyBatis-Plus 的租户插件自动加条件，PostgreSQL 行级安全（RLS）再兜一层底。
- 主键用应用生成的 UUIDv7；时间一律 `timestamptz`；弹性字段用 `jsonb`。
- 高频写（最后活动时间、心跳、反代计数）先在内存合并，几秒批量落库一次；请求路径上不做同步写。
- 定时作业（唤醒、备份、归档、导出）放进 PostgreSQL 作业表，`FOR UPDATE SKIP LOCKED` 领取，多副本不重复、重启不丢。

### 5.3 身份令牌

| 谁 | 拿的是什么 | 怎么校验 |
|---|---|---|
| 浏览器 | 不透明会话 cookie（主站、管理台各一个名字） | edge 查 NATS KV 缓存，没有再问 iam；吊销时 iam 删缓存并发事件 |
| 服务、外部系统 | OIDC 访问令牌（JWT，5 分钟） | 各服务用 iam 的公钥（JWKS）自行校验 |
| DSH 实例收到的请求 | edge 签的短期身份头（Ed25519，几十秒） | 插件用公钥校验；公钥由节点代理写进实例 |
| DSH 实例调平台 | 实例令牌（每个实例一个，可吊销） | edge 转给 workspace 校验 |
| 用户电脑上的插件 | 设备凭据（设备登录换得，可单独吊销） | iam |
| 平台调外部系统的 API（以后） | 打通时登记的服务凭据（加密保存）；对方支持时用令牌交换（RFC 8693）带上真实用户身份 | 由对方系统校验 |
| 节点代理 | 节点证书（mTLS，入网时用一次性令牌换取，自动轮换） | workspace |

- **身份头密钥轮换**：签名身份头带密钥编号（`kid`）。节点代理给实例写入"当前 + 下一把"两个公钥，轮换时 edge 先切到下一把，旧公钥过期后再移除，实例不用重启。
- **时钟**：身份头只有几十秒有效期，多台主机时所有节点必须开 NTP 时间同步；节点代理上报本机时钟偏差，超过 5 秒告警。

## 六、DSH 插件

npm 上单独发布，三种模式：

| 模式 | 适用 | 功能 |
|---|---|---|
| **离线版** `standalone` | 个人电脑上单独使用，不接团队 | 只有登录：应急账号 + 配置里的身份源连接器（企业定制连接器是其中一种），单一主人。没有团队功能，不连平台 |
| **托管** `managed` | 平台服务器上的实例 | 门锁（只认 edge 签名、主体等于实例主人）、守卫（拦截原生插件管理、越界新建工作区）、活动探针、"团队"面板外壳、团队 SDK 门面 |
| **连接** `connect` | 用户电脑接入平台 | 设备登录、本机只放行 loopback、团队面板外壳、按平台下发的清单接入团队 MCP 和团队模型 |

原则：插件里只放**必须在 DSH 进程里才能做**的事。团队界面由平台提供、插件只负责挂载；团队工具全部经 ai-gateway 的 MCP 提供（DSH 自带的 mcp-client 支持 Streamable HTTP，已有插件用这种方式接外部系统的 MCP，证明这条路可行）；资源同步、模型配置、目录迁移、文件读写都由节点代理在实例外面做。

原型插件里的密钥账号、会话存储（memory / redis）、资源同步、文件、知识沉淀、团队 agent、skill 凭据等代码，按上面的分工迁到平台或删掉。

补充约定：
- **协议版本**：插件和平台之间的协议（身份头、心跳、设备登录、面板加载）带版本号。平台同时支持当前和上一个大版本，因为用户电脑上的连接模式插件升级会慢；更旧的插件被拒绝访问团队资源并提示升级。
- **连接模式下的团队面板**：面板包从平台下载，校验平台签名后在本机加载；调用平台接口用设备凭据，平台的 CORS 白名单放行 DSH Desktop 的来源（`dsh-app://app`）和本机 loopback。
- **需要会话上下文的团队工具**：MCP 调用不一定带 DSH 的会话 id，而团队任务工具要知道"在为哪个任务干活"。开工前先验证 DSH 的 mcp-client 能否透传会话信息（开发计划里的 S1）；不能的话，这类工具由插件注册、再转发给平台。
- **SDK 服务名**：统一为 `ctx.get('auriga')`；原型的 `ctx.get('dshTeam')` 不保留，依赖它的插件一并修改。

**身份源**：插件离线版和平台用同一套身份源概念（见身份源文档第八节）。公开插件只带应急账号和通用 OIDC；企业定制连接器和企业配置由各企业单独分发。公开仓库里没有任何企业内部地址和系统编码。

## 七、数据库：PostgreSQL 内置或外置

| | 内置 `DB_MODE=bundled` | 外置 `DB_MODE=external` |
|---|---|---|
| 来源 | 安装包自带便携 PostgreSQL 17（Windows 便携包、Linux manylinux2014 编译） | 用户自己的 PostgreSQL ≥ 15，填连接串 |
| 安装时 | `initdb`，建库和每个服务的角色、schema，口令随机生成 | 探测连通、版本、权限；不通过不让继续 |
| 监听 | 127.0.0.1:15433（避开常见的 5432 和 15432，便于和其他产品装在同一台机器上） | — |
| Docker Compose | 带一个 postgres 容器，只在内部网络 | 去掉，填连接串 |
| 升级 | 跨大版本由安装器执行 `pg_upgrade`，之前自动备份 | 用户自己管 |
| 备份 | `ctl backup` 一次备齐：数据库、密钥、实例目录、对象存储 | 只备份密钥、实例目录、对象存储；数据库由用户备份 |
| 高可用 | 单机 | 用户提供高可用 PostgreSQL 后，平台各服务可以多副本 |
| 切换 | `ctl reconfigure-db` 在两种模式间切换，不删数据 | 同左 |

- 每个服务一个 schema、一个数据库角色，只授予自己 schema 的权限。
- 迁移用 Flyway，每个服务管自己的；启动时自动执行，多副本同时启动由 Flyway 的锁保证安全。
- **迁移遵循"先扩后缩"**：一个版本只加列、加表，删列、改名放到下一个版本，保证升级失败回退到上一版本程序时数据库仍然能用（单机安装包的"升级失败自动回滚"依赖这一点）。
- 模型 key、TOTP 密钥、外部身份源 token 等在应用层用主密钥加密后再入库；外置库的 DBA 只能看到密文。主密钥在数据目录，Windows 上用 DPAPI 保护。
- 以后可以验证 PostgreSQL 系的国产数据库（openGauss、金仓、瀚高）作为外置库，满足信创项目。

## 八、与外部系统打通（排在很靠后）

外部系统（例如运维平台）**各自独立，不并入平台、不合并代码**。以后需要时只做 API 层面的打通：

- 平台按需调对方的 API 取数据，对方也可以调平台的开放 API；
- 对方的凭据在平台里登记、加密保存；对方支持时再带上真实用户身份（令牌交换）；
- 取到的数据如果要给 agent 用，由 ai-gateway 包装成 MCP 工具提供给 DSH 实例。

现在要做的只有一件事：平台的开放 API 和服务账号从一开始就设计好（第十一节），打通时两边都有现成的接口。

在此之前，这类系统的 DSH 插件照旧是普通插件，可以经资源中心下发给需要的人。

## 九、部署形态

| 形态 | 组成 | 适用 |
|---|---|---|
| **单机安装包** | Windows：`Setup.exe`（Inno Setup）+ 每个组件一个 Windows 服务（WinSW）；Linux：离线 tar.gz + `install.sh` + `ctl` + systemd。都自带 JRE（jlink 裁剪）、Node、PostgreSQL、NATS 和全部 Go 服务，目标机器不用预装任何东西 | 公司服务器、几十人的团队、离线环境 |
| **Docker Compose** | 每个服务一个容器 | 有 Docker 的 Linux 服务器 |
| **Kubernetes** | Helm chart；DSH 实例以后可以加一个 Kubernetes 驱动 | 大客户、SaaS |

单机版的进程和权限：

| 服务 | 身份 | 说明 |
|---|---|---|
| PostgreSQL、NATS | 各自的低权限账号 | 只听 127.0.0.1 |
| Java 业务进程、edge、ai-gateway、egress、kb-server | 低权限服务账号（Windows 用虚拟服务账号） | edge 对外，其余只听本机或内部网络 |
| agent 节点代理 | root / LocalSystem | 不开 TCP 端口给外部；只接受 workspace 的指令（mTLS），并按本地策略校验 |

单机版平台自身占用估计：Java 0.6–1 GB、Go 服务合计约 0.2 GB、PostgreSQL 约 0.2 GB、NATS 约 0.05 GB，合计约 1.5 GB；DSH 实例另算（空闲约 0.2 GB 一个）。

运行时：Linux 推荐 Docker / Podman 跑实例（隔离最强）；Windows 用原生进程（每实例一个本地账号 + Job Object + 目录 ACL + 出站过滤），隔离强度低于容器，详见节点代理文档。

其他部署要求：
- **系统支持**：Linux 原生进程驱动要求 systemd ≥ 245 和 cgroup v2，CentOS 7 这类老系统只能用 Docker 驱动；Windows 支持 Server 2019 / 2022 / 2025 和 Windows 10 / 11。
- **证书**：有域名时 edge 用 CertMagic 自动申请和续期证书；也可以关掉 TLS，交给已有的反向代理。
- **高可用**（外置 PostgreSQL 时）：Java 服务和 edge 多副本；NATS 三节点集群；节点代理本身就是每台主机一个。

## 十、仓库与工程

**公开主仓库** `hansjone/auriga`：

```
auriga/
├─ services/            Java（Maven 多模块）
│  ├─ common/           共享：安全、租户、审计、事件、错误码
│  ├─ iam/  org/  workspace/  resource/  knowledge/  collab/  audit/  ops/
│  └─ platform-app/     合并部署启动器
├─ infra/               Go（go.work）
│  ├─ edge/  ai-gateway/  egress/  agent/  ctl/
├─ web/                 Vue（pnpm workspace）
│  ├─ portal/  admin/  panel/（嵌进 DSH 的团队面板）  shared/
├─ clients/dsh-plugin/  DSH 插件（Node，npm 包名 auriga-dsh，独立发布）
├─ contracts/           openapi/  proto/  events/（事件 schema）
├─ deploy/              windows/  linux/  compose/  helm/  examples/
├─ images/              实例镜像等
├─ test/                e2e/  compat/（DSH 兼容性）
└─ docs/                adr/（架构决策记录）  中英文文档
```

**私有仓库**：企业定制身份源连接器（平台用的 Java 版、插件离线版用的 JS 版）和企业配置；以后的企业版模块也放这里。

- 一开始就公开，所以从第一个提交起：不放内部地址、IP、账号；示例一律用占位符；CI 里加敏感信息扫描（gitleaks），扫到就失败。
- CI：GitHub Actions（Forgejo 镜像同步）；每次提交跑 Java / Go / 前端 / 插件测试、契约检查、架构测试、敏感信息扫描。
- 发布物：Windows `Setup.exe`、Linux tar.gz（x86_64 / arm64）、容器镜像（amd64 / arm64）、Helm chart、npm 插件包，统一带 sha256 和签名。

## 十一、商业化要素

| 要素 | 设计 |
|---|---|
| 版本划分 | 社区版（公开仓库，AGPL-3.0）和企业版（商业许可，含私有模块）。企业版模块的候选：多租户、SAML / LDAP / AD / 目录同步、高可用、合规审计导出、计量计费、高级运维 |

| 许可证管理 | 离线签名的许可证文件，限定用户数、节点数、功能；各服务通过 common 里的同一个检查点判断 |
| 多租户 | 数据模型现在就带 `tenant_id`（5.2）；私有部署单租户，SaaS 多租户 |
| 计量 | 模型 token、实例运行时长、存储用量都发计量事件，汇总后可导出账单 |
| 开放能力 | OpenAPI、服务账号和 API 令牌、Webhook、身份源连接器接口（Java 插件或任意语言的远程连接器） |
| 信创 | Linux arm64（鲲鹏、飞腾）、麒麟 / 统信；PostgreSQL 系国产数据库作为外置库选项 |
| 交付与运维 | 离线安装包、升级失败自动回滚、备份恢复演练、运维看板和告警、中英文文档 |
| 合规 | 审计按月分区、可导出、哈希链防篡改；敏感字段加密；数据导出和删除流程 |
