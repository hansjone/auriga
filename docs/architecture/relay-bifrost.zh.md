# 中转站：Bifrost 核心与 Auriga 身份

后端由 Auriga 维护，管理台使用自己的中文页面，不发布上游 UI。

严格预算请求当前只接受内联文本、普通本地函数工具及其文本结果。图片、音视频、文件、加密/不透明历史、服务器取文/搜索/代码执行/MCP等工具以及未知扩展，在预算准入和供应商派发前拒绝；这是整份请求的正向校验，不依赖工具名称黑名单。本地函数即使叫`web_fetch`也可正常使用；标准函数选择和内联JSON输出schema保留，schema引用限本地片段。失败使用`common.validation_failed`，`params.field`指向`/messages`、`/tools`、`/tool_choice`或`/response_format`等具体入口。远程内容或服务器工具追加的实际Token不能由URL/请求字节或pool能力提示证明上界；可信动态输入计量尚未接入，不能用增大估计常数代替。仅计量成员保上游媒体和服务器工具语义，不受此预算路径限制，确认用量照常记录。

模型上下文能力的合法值为0（未知）或至少2；管理台、导入和后端均拒绝1，公开目录也不发布历史无效的1，避免一个池破坏整个客户端目录。

成员调用仍走门户 `/ai/v1`，经 edge 和 ai-gateway 在线校验 IAM、组织权限和设备/托管身份，再按租户与成员确保唯一虚拟 Key。每次确保都读当前状态，禁止自动复活被禁用的 Key，也不覆盖管理员已设预算。成员虚拟 Key 不能单独从公网使用：edge 仅接受 external 来源，后端对 member 来源还要求身份桥的服务认证。

外部调用使用管理员签发的 `sk-bf-` Key，经门户相同 `/ai/v1/chat/completions`、`/ai/v1/models` 入口。edge 每次在线查 Key 来源和状态，没有允许缓存；调用方不能传入供应商地址、供应商密钥或自动切换目标。归属信息由服务覆盖。

管理接口位于管理员来源 `/api/ai/v1/admin/relay`，edge 每次重新内省平台会话并检查权限；写入必须同源、CSRF、10分钟内二次验证，跨成员用量查询也须近期二次验证。管理上游仅在 Docker 私网，浏览器不能直接访问。内网管理口令只交给 edge；成员身份桥只持独立成员口令，无法调用管理接口。后端从可信 access.json 绑定安装租户，管理头和成员请求均不能跨安装租户。

后端是 `infra/ai-gateway/cmd/relay-backend`，只借 Bifrost core/providers，不含 transports/framework/plugins。每次请求加载不可变路由快照，使用上游加权选择器、worker、fallback、SSE 解析；禁用供应商和密钥变更在后续请求生效。请求与结算都有期限；下游断开后取消并等待 worker 结束。

一个公开别名可以包含同一供应商的多个不同模型。路由按“供应商 ID + 上游真实模型 ID”去重，权重选择以每条路由为单位；同供应商的其他模型也参与故障切换。完全相同的路由应合并权重，不能重复添加。

供应商种类决定内部协议：`openai` 默认经 Bifrost 既有转换使用 Responses，`openai-compatible` 保持 Chat Completions，其他厂商沿原生适配。选择不按模型名特判，每次故障切换按当前供应商重新判断；对外仍只有现有 Chat 入口，回复保留公开池别名。显式 stop、seed、多候选、惩罚、logprobs、音频、prediction、web_search_options 等无法等价转换的 Chat 参数保留 Chat 路径；这不保证每个上游型号都支持这些参数。原生 OpenAI 在这条路径只给序列化输入副本标明基类，避免供应商别名误触发通用兼容过滤；路由、凭据与回退身份不变。

只支持 Chat 的旧 OpenAI 型号可另配 `openai-compatible` 供应商；修改已有供应商种类会清凭据，须按正常流程重新录入。未知型号按所选协议请求，不按名称猜能力，也不在协议失败后盲目重发。SDK 原有 Responses 显式小于16的输出值规范化为16，缺省不注入输出值；legacy `user` 沿 SDK 既有转换约定，`safety_identifier` 和 `prompt_cache_key` 各自保留语义。Run 目前只解析已知参数，未知顶层 JSON 扩展没有提取到 SDK 的 `ExtraParams`；SDK 内部显式 `ExtraParams` 的转换行为保留，不能据此宣称公开入口支持任意字段透传。这批以假上游矩阵验证接线，不代表模型目录中全部型号均已真实付费验证。

预算预占须覆盖上述 SDK 协议下限：显式输出值小于16且任一可达路由为原生 OpenAI 时，保守按16预占，包含零权重故障兜底；只有compatible或其他厂商时仍按原值。它只调整内部预占估计，不改调用方正文、不取目录推荐值作限制；成功后按实际确认用量结算并释放预占。

主密钥经 HKDF 独立派生签名键和加密键；虚拟 Key 使用 HMAC，数据库不存明文。供应商凭据与管理幂等响应使用 AES-GCM，密文带格式版本1，租户/记录 ID 为 AAD。外发 user 使用 HMAC 匿名标识。修改供应商根地址或种类会清除原凭据，必须重新录入。管理 POST 必须 Idempotency-Key，同租户同键不同内容409；崩溃后的未完成声明保持阻塞，避免重复签发。五个独立文件秘密由部署工具首次生成并拒绝隐式旋转。

PostgreSQL 独立 bifrost 数据库，迁移 owner 与运行账号/口令分离，表强制租户 RLS。用量复用原有账本和 outbox，不保存提示词正文。新成员默认 `meteringOnly=true`：保每次在线身份、模型权限与吊销检查，保幂等和派发CAS，按上游确认用量记账；不预占金额、不设RPM/并发/在途Token业务限制。`BudgetAdmission.metering_only`随原持久化protobuf保存，重启不会把估计值误当上限。

管理台可显式关闭成员“仅计量”，启用明确的预算与流量治理。`monthlyBudgetMicros=0`仍表示禁止，不能据0推断不限；流量参数0或未指定表示不限，显式非零值继续执行。对外Key不能开启仅计量模式，仍保明确月预算；预算调用须指定`max_tokens`或`max_completion_tokens`，按请求预留，不再用池的能力信息拒绝或注入4096。实际供应商用量、价格冲突及未知费用仍按严格账本处理。RPM和预算采用数据库行锁，不用进程计数替代。

`policyOrigin=default`的成员跟随身份桥默认配置；正常管理员保存后标为`administrator`，ensure不会覆盖。历史没有来源标记的成员按`legacy`保留；无法从旧值可靠区分人工配置与自动默认，应由管理员在正常页面明确切换，不按数值猜测或复活已禁用成员。

池上下文与最大输出是发布给DSH与外部调用方的能力元数据。新建/导入默认继承所选供应商真实模型，能力来源默认首条正权重路由，可明确选择池内其他来源；不取全部路由或权重0兜底的最小值。每个维度均可改为手动覆盖；继承项优先上游明确返回的字段，缺失时使用管理员配置的推荐值，再缺才是未知0，公开目录省略未知字段。旧模型池没有capabilities配置时保留原明确值，不静默覆盖已有1M等配置。输入上限与总上下文分别表达，不能取min或相加推算；只有输入上限时如实提示，仍可配置推荐总上下文。

管理页“从上游更新能力”重新读取所选来源目录，只更新上游快照和继承项，保留手动覆盖；成功刷新缺失字段会清掉旧字段，改用推荐值或未知。网络失败保留原快照并显示失败。换来源或移除来源路由不能沿用另一个真实模型的快照。选择、模式、推荐值与快照随正常保存写入现有模型池文档；刷新后须保存发布，重新打开可读回。成员与外部Key共用/v1/models的同一脱敏投影，只按已有授权过滤；公开目录不包含供应商ID、真实模型ID或凭据。DSH在原生设置手动同步即可，无需后台热更新、重建客户端或重启实例。

这些能力、推荐或覆盖值不裁限中转请求，也不自动注入输出值；调用方与上游决定实际上下文和输出。JSON请求仍有32MiB传输边界，管理写保持1MiB；不再按1000条消息截住合法历史。请求和流空闲仍有期限，不能把“不设Token业务限额”说成传输资源无限。标准OpenAI模型目录可能只提供ID；没有能力字段时不按模型名字猜32K/4096，可由管理员设置推荐值。

断流/超时优先使用确认用量；缺失时记录`estimated`，不能冒供应商账单。严格预算请求遗留超过10分钟且派发令牌过期8分钟后仍按原保守预占结算，未知执行不能仅凭超时退款；仅计量模式没有冻结额度，未知状态也不会新增配额围栏。

部署：compose 直接构建 Dockerfile.bifrost；NAS bundle 增加 bifrost/operator 镜像并按不可变 ID 加载，不临时拉取。operator 仅供既有管理员初始化/应急工具，模型服务没有 Python。内网服务不发布宿主端口。新部署不再需要 relay 域名或 relayAdmin listener。

测试环境不迁移 LiteLLM 数据。更新前由主控保留所需现场证据，重建生成材料和镜像；旧 LiteLLM 数据/秘密/UI发布材料的现场删除另由主控处理，工人不操作 VPS、DNS、NAS 数据或真实 DSH profile。

本机验收入口：设置独立测试 PG 的 AURIGA_AI_TEST_PG_DSN 后，在 infra/ai-gateway 执行 `go test -count=1 ./internal/bifrostbackend ./internal/bifrost ./internal/modelgate ./internal/budget ./internal/store`。其中假供应商对话是真实 Bifrost 数据路径，真实 PG 会记录用量；这不等于真实 MiniMax/DeepSeek、桌面/云端 DSH、公网或 NAS 现场验收。

已知限制：第一步供应商配置仅包含名称/种类/根地址/启停，网络期限和 worker 数量使用服务固定上限。上游当前每请求创建 core（没有跨请求连接池）；不同 fallback 尝试的未知费用不能从最终成功 usage 中推断。现场发布前须审查并补验这些边界。用量 providerId/credentialId 表示派发前预占快照，不是 fallback 实际选中路由；池价是管理员统一向调用方计价，不代表供应商采购成本。跨供应商真实成本与逐尝试归属需另行扩展事件契约，当前不将其冒充供应商账单。管理幂等崩溃记录保留阻塞、503可重放；没有自动删除 in-progress，因为变更可能已提交，盲目超时重试会重复签发。需人工核对后使用新幂等键。密文格式版本不是主密钥轮换功能；轮换需要停写、重加密及令牌换发方案，禁止直接替换材料。

已有 PostgreSQL 卷的升级：先生成并保护新的五份中转站材料、加载审核镜像，确保原 postgres 健康，再运行 `sh deploy/nas/scripts/upgrade-bifrost.sh`（Compose 为 `sh deploy/compose/scripts/upgrade-bifrost.sh`）。脚本仅启动一次性 psql helper，幂等创建隔离角色、数据库和 schema，不清卷、不重启原库、不更改已有角色密码；错误 owner 或特权角色会拒绝升级。成功后再更新 Bifrost/ai-relay/edge。旧测试数据库和秘密不迁移，清理由主控单独批准。

安装材料边界：数据库脚本不迁移已封存收据。旧 NAS 安装通过公开 `scripts/materials-upgrade.sh` 显式 stage，再 render/建库/切换，验收后 commit。原 identity、TLS、runtime根和collab收据保持原字节；新增秘密/运行配置在独立目录，升级与激活记录按版本和哈希链追加，失败在commit前rollback并恢复旧服务。不能删除收据、重建CA或覆盖原身份绕过门禁。具体操作与异常恢复见 [NAS说明](../dev/nas.md#已有数据库卷接入中转站)。
