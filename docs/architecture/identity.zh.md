# 身份源架构设计（v0.1，2026-10-19）

> 总体架构见 [platform.zh.md](platform.zh.md)。"平台"即 Auriga。

---

## 一、目标

1. **一套身份架构**。平台自带的"团队账号"是一个身份源，企业自建的统一认证系统是另一个身份源，以后的微信、QQ、钉钉、飞书、企业微信、LDAP、OIDC、SAML 也都是身份源，**地位相同、接法相同**。
2. **企业自建系统只是其中一种**。平台代码里没有任何特定企业的专用逻辑；企业自建的认证系统通过"企业定制连接器"接入，连接器放各企业自己的仓库。
3. **开源后别人好接**：
   - 用标准协议的公司（OIDC、SAML、CAS、LDAP）只需在管理台填配置，不写代码；
   - 微信、QQ 这类常见平台预置好模板，填 AppID 和密钥就行；
   - 协议特殊的公司写一个连接器插件，不改平台代码。连接器可以是 Java 插件，也可以是任意语言写的独立 HTTP 服务。
4. **插件离线版用同一套概念**：应急账号 + 可插拔的连接器（企业定制连接器是其中一种）。

原型的写法是每个身份来源自己注册路由、自己发会话（本地账号、企业扫码、应急账号、密钥账号各管一摊），加一种登录方式就要改核心代码。新架构把这些拆成"平台核心 + 连接器"。

---

## 二、核心模型

```
 账号 Account（平台里的一个人，uid）
   │ 1 : N
   ▼
 身份 Identity（某个身份源里的一个主体：provider + subject）
   │ N : 1
   ▼
 身份源实例 Provider（连接器类型 + 一份配置，例如"公司统一认证"、"微信扫码"、"客户 A 的 OIDC"）
   │ N : 1
   ▼
 连接器 Connector（代码：知道怎么跟某种外部认证系统打交道）
```

- **账号和身份分开**：一个人可以绑定多个身份，例如既能用公司统一认证扫码，也能用微信登录，进的是同一个账号、同一个实例。
- **同一种连接器可以配多个实例**：比如接了两家客户的 OIDC。
- **身份源实例归属租户**：同一个外部主体在不同租户里是不同的身份。

| 表（iam schema） | 内容 |
|---|---|
| `idp_provider` | 租户、连接器类型、名称、显示（图标、排序、按钮文字）、配置（jsonb）、密钥（加密）、启用状态、准入策略 |
| `identity` | 租户、身份源实例、外部主体 id、账号、外部属性快照（jsonb）、最近登录时间 |
| `login_tx` | 登录事务：当前步骤、身份源、状态参数（state / nonce / PKCE / 二维码挑战）、发起端绑定信息、5 分钟过期 |
| `account_link_log` | 绑定、解绑记录 |

连接器类型本身不入库，由代码（或远程连接器的注册信息）提供。

## 三、连接器分类

| 类别 | 例子 | 接入方式 | 放在哪 |
|---|---|---|---|
| **内置** | 团队账号（邀请注册、口令 + TOTP、Passkey、手机扫码确认）、应急账号 | 平台自带。应急账号不能关、不能删 | 公开仓库 |
| **标准协议** | OIDC、OAuth 2.0、SAML 2.0、CAS、LDAP / AD | 管理台填配置 | 公开仓库 |
| **预置模板** | 微信（开放平台网站应用扫码）、企业微信、QQ 互联、钉钉、飞书、GitHub、Google、Microsoft Entra ID | 基于 OAuth 2.0 / OIDC 的配置模板，填 AppID 和密钥 | 公开仓库 |
| **企业定制** | 企业自建的统一认证（扫码、搜人、下游凭据） | 写连接器插件 | 各企业自己的仓库 |

预置模板的资质由部署方自己办：微信开放平台网站应用要企业主体认证和审核；QQ 互联要已备案的域名。微信用 `unionid`（同一主体下各应用一致）作为外部主体 id，没有时才用 `openid`。

## 四、登录的交互方式

所有连接器的登录过程都表示成一串**步骤**，前端只认步骤类型，不认连接器。加新的身份源不用改登录页。

| 步骤 | 用于 | 前端怎么做 |
|---|---|---|
| `redirect` | OIDC、OAuth、SAML、CAS、微信、QQ、钉钉、飞书…… | 跳转到外部地址，回调后继续 |
| `qr` | 企业扫码、内置扫码、微信内嵌二维码 | 显示二维码和两位比对码，订阅事务状态（SSE），手机确认后继续 |
| `form` | 口令、LDAP | 按字段定义渲染表单，提交后继续 |
| `webauthn` | Passkey | 调浏览器 WebAuthn 接口 |
| `device` | DSH 连接模式、命令行 | 设备码流程（RFC 8628）：显示用户码，在另一台设备上确认 |
| `done` | 连接器拿到了外部身份 | 交给平台核心（第六节） |
| `fail` | 出错 | 显示统一的错误码和文案 |

一次登录可以有多步：口令通过后要 TOTP；外部身份第一次出现时要求绑定已有账号；身份源要求二次验证时补一次 Passkey。这些都是同一个登录事务里的后续步骤。

## 五、连接器接口

### 5.1 Java 插件（进程内）

```java
public interface IdentityConnector {
    ConnectorDescriptor descriptor();   // 类型、显示名、图标、支持的步骤、配置的 JSON Schema、可选能力、SPI 版本
    void validateConfig(ProviderConfig config);
    LoginStep begin(LoginContext ctx, ProviderConfig config);
    LoginStep advance(LoginContext ctx, ProviderConfig config, StepInput input); // 回调参数 / 表单 / 扫码轮询
}

// 步骤：Redirect(url) | Qr(content, matchCode) | Form(fields) | WebAuthn(options) | Done(ExternalProfile) | Fail(code)
// ExternalProfile：subject、显示名、邮箱、手机、组织属性、原始声明、本次是否已做过多因素验证

// 可选能力
interface DirectoryCapability   { search(query); lookup(subject); changesSince(cursor); } // 邀请时搜人、离职同步
interface SessionCheckCapability { boolean stillValid(Identity identity); }             // 定期复核外部会话
interface CredentialCapability  { DownstreamCredential issue(Identity identity, String audience); } // 给 skill 的下游凭据
```

- 连接器**只负责翻译**：把外部协议转换成 `ExternalProfile`。它不碰数据库、不发会话、不判断谁能进，这些都由平台核心统一处理。连接器写起来小，出问题影响也小。
- 用 Java ServiceLoader 加载，插件 jar 放 `plugins/identity/`，每个插件独立的类加载器；`spiVersion` 不兼容的拒绝加载并在管理台提示。
- 管理台按 `descriptor()` 里的 JSON Schema 自动生成配置表单；标了 `x-secret` 的字段加密保存、界面上不回显。

### 5.2 远程连接器（任意语言）

不会写 Java 的公司，可以用任何语言写一个小服务，实现同样语义的 HTTP 接口：

```
GET  /descriptor                  → ConnectorDescriptor
POST /validate-config             → ok / 错误
POST /begin    { ctx, config }    → LoginStep
POST /advance  { ctx, config, input } → LoginStep
（可选）/directory/search、/session/check、/credential/issue
```

平台和远程连接器之间用 mTLS 或签名请求；远程连接器在管理台登记地址后，就和进程内连接器一样出现在类型列表里。

### 5.3 连接器测试套件

公开仓库提供一套连接器测试（TCK）：用模拟的外部系统逐项检查步骤流转、错误码、超时、重放、配置校验。第三方写好连接器跑一遍就知道能不能用。我们自己维护的企业定制连接器也要通过它。

## 六、平台核心：拿到外部身份之后

```
Done(ExternalProfile)
  │
  ├─ 1. 找身份：(身份源实例, subject) → 账号
  │     找不到时按该身份源的准入策略：
  │       · 邀请：登录事务里带着邀请码 → 建账号并绑定
  │       · 自动开通：外部属性符合规则（例如邮箱域名、组织）→ 建账号
  │       · 绑定：当前已登录 → 经二次验证后绑到当前账号
  │       · 否则拒绝，提示联系管理员
  ├─ 2. 检查账号状态（停用、离职）
  ├─ 3. 多因素：该身份源要求二次验证、而本次外部登录没做过 → 追加 TOTP / Passkey 步骤
  ├─ 4. 同步属性：姓名、邮箱；部门 → 组（按映射规则）
  ├─ 5. 发会话（平台统一格式，与身份源无关）
  └─ 6. 审计 + 事件 identity.login（带身份源）
```

每个身份源实例的**准入策略**：

| 项 | 例子 |
|---|---|
| 谁能进 | 只有受邀的人 / 符合规则的自动开通 / 只允许已绑定的 |
| 默认身份类型 | 正式成员 / 外部协作者（按信任程度区分，不按登录方式区分） |
| 属性映射 | `dept` → 组；`email` 域名 → 租户 |
| 二次验证 | 不要求 / 每次要求 / 新设备要求 |
| 会话时长 | 例如企业统一认证 8 小时，微信 7 天 |
| 外部会话复核 | 每隔多久检查一次外部会话还在不在（外部会话失效时平台会话一起失效） |

## 七、下游凭据

原型里 skill 直接拿着用户的企业认证 token 去调公司系统。这件事通用化为**凭据代理**：

1. skill 通过插件 SDK 请求"以本人身份访问某个目标"（目标在管理台登记：地址白名单、对应哪个身份源）。
2. 平台调该身份源连接器的 `CredentialCapability` 拿到凭据。
3. **优先由平台代发请求**、把凭据注入请求头，凭据不进实例；目标系统确实需要客户端自己持有时，才下发短期凭据。
4. 每次使用都审计。

第一个实现这项能力的是一个企业定制连接器；以后企业微信、钉钉的开放接口也可以用同样方式给 skill 用。

## 八、插件离线版

离线版不连平台，但用同样的概念：

| 项 | 做法 |
|---|---|
| 身份源 | 内置的应急账号 + 配置里列出的连接器 |
| 连接器 | JS 实现，接口和第五节相同（步骤的 JSON 格式一致，定义在公开仓库的 `contracts/identity`）。公开插件只带应急账号和通用 OIDC；企业定制的 JS 连接器由企业单独分发 |
| 配置 | `connectors: [{ type: example-sso, module: '<企业私有包名>', config: { … } }]` |
| 主人 | 第一次成功登录的身份成为主人；之后只有绑定在主人名下的身份能登录（沿用原型的主人绑定） |
| 下游凭据 | 只在本机：连接器把凭据交给本机 skill，不经过平台 |

离线版不需要平台里的账号、组、准入策略这些概念：单一主人，够用就行。

## 九、安全要求

- 跳转类流程一律带 `state`、`nonce` 和 PKCE；回调地址按身份源固定，不接受参数指定。
- 扫码类流程绑定发起端（两位比对码 + 发起端 cookie），防止二维码被转发后在别人的浏览器里登录。
- 登录事务 5 分钟过期、一次性使用；按 IP 和账号限速。
- 绑定新身份、解绑身份需要二次验证；不能解绑最后一个身份。
- 应急账号每次登录强制 TOTP，并通知所有超管（沿用）。
- 连接器的密钥字段加密保存；连接器的每次外部调用记录耗时和结果（不记凭据）。

## 十、原型代码怎么处理

| 现在 | 新架构 |
|---|---|
| 本地账号（自建账号、Passkey、TOTP、扫码） | 内置连接器"团队账号" |
| 应急账号 | 内置连接器"应急账号" |
| 企业扫码登录（扫码、搜人） | 企业定制连接器，放私有仓库；搜人实现 `DirectoryCapability` |
| 密钥账号 | 删除。兜底由应急账号负责 |
| 插件里的企业接口代理、`skill-credentials`、`agent-auth` | 平台的凭据代理 + 企业定制连接器的 `CredentialCapability`；离线版里是 JS 连接器 |
