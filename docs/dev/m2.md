# M2 单机集成（Compose：能给每人起 DSH）

用 Docker Compose 把 platform（iam+org+workspace combined）、edge、NATS、PostgreSQL、节点代理（Docker 驱动）串起来，端到端验证：登录 → 冷启动 → 经 edge 访问实例 → 闲置回收 → 闹钟唤醒 → 双会话吊销。

Windows 侧不假设有 Docker CLI；本机 WSL 的 Linux Docker 或 GitHub Actions（`e2e.yml`）可运行完整栈。使用前先确认连接的是本机 daemon。有 Docker 的 Linux 可按下面步骤本机跑。

## Network submit 上游

新 bootstrap 同时生成私有 `var/network/`，材料纳入安装 receipt；重复 prepare 保留原凭据，缺失/漂移拒绝，不隐式修复旧安装。升级此配方须使用新的隔离材料目录和测试栈，保留原有数据，不手改 receipt。该目录为 `0700`、文件为 `0600`，含专用服务端 CA、submit 客户端 CA、叶证书、Broker NKeys/三组密码、协议签名私钥及固定 ai-gateway 服务票据导出配置。CA 私钥不落盘；submit 信任不与 IAM 共用。

edge 镜像附带已锁定依赖构建的 ai-gateway、network Broker 和无凭据就绪探针；Compose 用独立 `network-broker`、`network` 服务启动，分别执行正式 Broker 配置与 `--network-config`。network 与 callout/router 共享同一进程，Broker TCP 仅监听回环 `127.0.0.1:14224`，WSS 与 submit 分别在固定 Docker 网桥网关 `172.29.240.1:18444`、`172.29.240.1:18443` 提供 TLS 与强制 mTLS。submit HTTPS 端口只供持有专用客户端证书的 edge 访问，不将设备 Bearer 经明文传输。<!-- gitleaks:allow disposable M2 bridge, not a deployment address -->

edge 的 `upstreams.network-submit=https://172.29.240.1:18443`，`networkSubmitHop.serverName=submit.network.internal`；只挂载 `var/network-edge` 中的 edge 客户端证书/私钥和服务端 CA，读权限限定到 edge 组，不挂载 Broker 密码、服务端私钥或 ai-gateway 安装秘密。platform 从私有 `platform.properties` 启用现有固定 ai-gateway 票据导出，票据目录单独挂载并原子轮换；network 对 IAM RPC 仍使用 IAM 专用客户端证书。<!-- gitleaks:allow disposable M2 bridge, not a deployment address -->

network 健康检查经真实 mTLS POST 取得 `401 network.unauthorized` 后才启动 edge。`docker compose ps`、`stop`/`down` 覆盖两个新服务；不增加 `down -v` 或删除安装材料。此配方验证部署入口，不自动配置完整 collab 网络业务/协议信任发布；健康状态不等于真实设备 READY、持久化投递或双 DSH 闭环通过。

## DSH 运行时

M2 的 agent 经 `https://127.0.0.1:7443` 完成实际 CA pin TLS Join，
`ALLOW_INSECURE=true` 只允许旧开发入口，不会降级此 HTTPS 连接。
RT1 要求该响应含非空合法发行根。新空安装的 bootstrap 在进程内独立生成
`e2e-runtime-root`，只保存公开的 `var/runtime-keys/root.pb`，私钥不落盘、不输出，
不复用 IAM 身份 key。Compose 仅将该目录只读挂入 workspace 的既有 artifact-keys-directory。
根固定截止为 2031-01-01T00:00:00Z，并纳入原安装 receipt；重入只验证，
不滚动延长、不补旧 receipt 缺叶、不修复漂移。旧安装缺该材料时必须明确使用新安装目录，
不要手改 receipt。该根仅属于本次开发安装；bootstrap 在同一进程生成独立 Ed25519 私钥，为本次确切镜像签正式 RuntimeReleaseEnvelope 后立即清除私钥，不保留再次签发能力，
M2 仍不构成 RT2 安装/缓存/重启前发行校验的验收。

默认使用**极简假 DSH**（`deploy/compose/fake-dsh`）：Node HTTP + 最小 WebSocket echo，提供 `/_auriga/health` 与身份头校验，**不是** S4 真实 DSH 离线包，也**没有**真实插件 / Cordis 链路。真实模式需使用下节的 fixture、版本元数据和 `DSH_FIXTURE=real`，不能只换镜像后继续沿用假响应断言或代发心跳。

本验收**不能**解读为「真实 DSH / 真实托管插件已通过」。

## 真实 DSH 与托管插件（W3）

真实模式使用固定Linux镜像、当前renderer实际补丁、独立internal网络、非root uid、只读根和只读meta。它在完整生命周期前直接检查实际Docker加固参数、网络归属及仅实例/受信edge两个成员。验收结果以**对应固定源码与镜像**的脱敏`w3-evidence.json`为准：只有status=passed、rawHeartbeatVerified=true、lifecycleVerified=true全部成立，才能报告该轮真实HTTP交互和生命周期通过。现有E2E M2工作流默认仍验证假DSH；库测试、镜像构建或部分成功都不能替代真实运行，也不能据此声称NAS已部署。

### 构建输入与摘要交付

`real-dsh/versions.json` 记录 S4 分支提交、DSH **0.2.0-rc.2**、Node **22.19.0**、npm **10.9.3**、目标 **Linux amd64 / glibc**。完整 npm v3 锁原样取自 S4，SHA-256：

```text
7568ed6aeb263e8605332578aba9b3b099974bf2b80704afd92cc86b7afc168b
```

构建必须显式提供 `node:22.19.0-bookworm-slim@sha256:<64位摘要>`，脚本拒绝浮动 tag，并要求它与 `versions.json` 的 `nodeImage` 完全相等。该字段记录从 Docker 官方 registry 的固定 tag 解析得到的 Linux amd64 摘要、日期和命令，**独立审查仍为 pending**，来源解析不等于审批。Docker 构建实际核对 Node/npm 版本、锁摘要、每项 npm resolved/integrity，再以 `npm ci --omit=dev --include=optional --ignore-scripts --bin-links=false` 安装目标平台依赖；保留 S4 的可选原生包与执行权限处理。不支持 Alpine/musl 或 arm64。

插件源码只复制 `clients/dsh-plugin/src`、包描述与许可证。仓库已有插件 lock 的开发依赖范围与 package.json 不同步，构建只从该锁派生生产锁：去掉 dev 条目、校验直接生产版本与 package.json 精确相等，保持全部生产包的 resolved/integrity，不重新解析版本。两个锁的摘要均记入 manifest。构建上下文不复制用户 `.dsh`、公司 profile、凭据、模型配置或宿主 node_modules。

`scripts/build-real-dsh.mjs` 先将 Dockerfile 明确需要的源码/锁/元数据复制到临时白名单上下文（约 595 KB），不把根 node_modules、var 或 .git 发给 daemon；构建后清理该临时上下文。推送本地 registry 后从 RepoDigests 取得固定镜像引用，写 `var/real-dsh.json`，其中包括镜像与基础镜像摘要、版本、锁摘要和安装文件摘要清单。这个文件与对应镜像是交给 D0/主控的边界。公开构建流程会推送本机 registry 并取得精确 RepoDigest；取得制品摘要不代表完整真实 M2 或 NAS 验收完成。镜像摘要覆盖最终启动器；镜像内 `/opt/fixture/manifest.json` 是构建输入清单，不是原始 OCI manifest，也不能替代发行签名。公开 prepare 流程另从本次本地 registry 精确仓库和 digest 读取原始单平台 OCI/schema2 manifest 及其 descriptor 对应的 config，核原字节 SHA-256、descriptor 长度和 linux/amd64 平台；拒绝 index/list、重复 JSON 键、外部 URLs/data、重定向和每文件超过 4 MiB 的材料。

启动入口为 `real-dsh/start.mjs`，使用镜像内 Node 启动原版 DSH `web --patch /run/auriga/cordis.patch.yml --no-open`，即节点代理渲染的补丁（不再带 fixture 自带补丁）。`--patch` 必须放在 web app 的 `--no-open` 参数之前，否则 launcher 会把它透传并报未知参数。DSH 0.2.0-rc.2 的命令行拒绝 `--host 0.0.0.0`，所以监听地址由渲染补丁的 `webserver` 行给出（Docker 运行时 `0.0.0.0`，原生进程 `127.0.0.1`），同一补丁用包根行 `id: auriga-dsh` / `name: auriga-dsh` 装载插件、写入 `trustedHosts`。包根必须配套导出 Cordis 入口 `src/plugin.js`（当前插件 manifest 已声明）；同版本收集器补证见 [PR118 记录](pr118-dsh-collector.md)，不代表托管镜像/现场已验收。原生包、插件与前端均在构建期准备；实例启动不执行 npm/pnpm。

DSH 的模块解析只接受安装/profile manifest 的依赖闭包，单独的安装目录 symlink 不足以装载插件。因此该固定 fixture 启动时物化专属 web profile manifest，只声明镜像中预装的 `auriga-dsh`，并链接到该预装目录；不会下载或安装依赖。它不能代替通用生产插件的安装、启停或用户 profile 合并验收。HOME、DSH_HOME、缓存、临时目录及工作空间都放在 `/home/dsh` 可写挂载中；本机 WSL 验证用 Linux 原生临时目录，Windows 盘挂载显示的 0777 会被 DSH credentials-local 拒绝。运行时使用 agent 分配的非 root uid、只读根文件系统与独立内部网络；补丁关闭原生启动 URL 输出，遥测保持禁用。

### Linux 复现（独占的新 M2 测试栈）

不要在已有数据的环境直接切换 fake/real。以下命令仅供有 Docker 的本地 Linux 测试环境，工人未执行；需预装仓库要求的 Java/Go/Node 工具链。先由主控解决下节接线缺口，再运行：

```bash
cd <auriga-worktree>
export COMPOSE_PROJECT_NAME=auriga-m2-new-run
export AURIGA_M2_DATA_ROOT=/var/lib/auriga-m2-new-run
export NODE_IMAGE="$(node -p 'require("./deploy/compose/real-dsh/versions.json").nodeImage')"
# versions.json 记录官方 registry 的 linux/amd64 摘要与来源；独立审查仍待完成。
export DSH_FIXTURE=real
export AURIGA_M2_HEARTBEAT_OBSERVER=1
bash deploy/compose/scripts/prepare.sh
set -a; source deploy/compose/var/compose.env; set +a
export RAW_HEARTBEAT_FILE="$PWD/deploy/compose/var/raw-heartbeats.jsonl"
node deploy/compose/scripts/heartbeat-observer.mjs &
OBSERVER_PID=$!
trap 'kill "$OBSERVER_PID" 2>/dev/null || true' EXIT
docker compose -f deploy/compose/docker-compose.yml --env-file deploy/compose/var/compose.env up -d --build --wait
sh deploy/compose/var/iam-healthcheck.sh
# platform 首次生成的应急 enrollment 需当前测试用户可读；不要打印内容。
AGENT_VOLUME="$AURIGA_M2_DATA_ROOT" \
  ENROLLMENT_FILE=deploy/compose/var/enrollment/emergency-enrollment.json \
  JOIN_TOKEN_FILE=deploy/compose/var/join/token \
  node e2e/m2.mjs
docker compose -f deploy/compose/docker-compose.yml --env-file deploy/compose/var/compose.env down -v
```

`prepare.sh` 在 real 模式自动构建、推送并选用真实模板，模板版本/名称/标签同步变化；默认 fake 行为保留。

fake/real 构建都显式设置 `--platform=linux/amd64 --provenance=false --sbom=false`，避免 BuildKit 默认 attestation 将单平台输出包装成 index；发布后仍以 registry 实际返回的单平台 manifest digest 为准，collector 继续拒绝 index/list，不替换成未经本次引用绑定的 child 摘要。fake/real 都经 `scripts/collect-runtime-proofs.mjs <image> <隔离临时根>` 收集公开原字节；CLI 只接受 `127.0.0.1:5000/auriga/{fake,real}-dsh@sha256:<64位小写hex>`，不接受任意 registry、仓库或 URL。prepare 将临时根通过 bootstrap 的 `-runtime-proofs` 参数交给首次新安装；bootstrap 校验后创建 `var/runtime-proofs/<manifesthex>/manifest.json` 与 `config.json`，receipt 覆盖两份原始文件和正式模板。producer 在 manifest/descriptor、config/rootfs/history/执行与历史 config/healthcheck 的结构边界拒绝非规范 ASCII、long-s、Kelvin simple-fold 别名；仅严格结构对象使用既定允许字段，Labels、annotations、ExposedPorts、Volumes 的用户键与合法元数据扩展保持原样。Compose 将公开 proof 目录只读挂到 `/etc/auriga/runtime-proofs`，可信本机变量 `AURIGA_AGENT_RUNTIME_PROOFS_DIR` 指向该路径；通用安装可将按受签摘要核验的相同原始 M/C 放到 agent 默认 `<AgentDir>/runtime-proofs/<manifesthex>/`，不能用 Docker save 输出或重序列化 JSON 代替。proof 目录无私钥，目录本身不赋予信任。

Docker-only 模板的 `dsh.digest`、`dsh.url`、`releaseEnvelope.archiveDigest` 全空，旧 `SignedArtifact` 不存在；正式 envelope 固定 `purpose=dsh_runtime,name=dsh,os=linux,arch=amd64,releaseSequence=1`，`artifactId/dshVersion` 对应所选 fixture，`imageDigest` 绑定实际 manifest。首次安装的独立 runtime root 私钥仅在本进程完成正式 JCS/Ed25519 签名后清除，不使用 IAM 密钥或固定测试密钥。WorkspaceTemplates 校验正式声明的形状、映射和平台筛选；它不持有 agent 的可信 keyring，不构成验签。agent 最终按固定信任根验签、核 OCI 与实际执行镜像。

重入先严格验证原 receipt、公开根、模板和原 proof，并只读核保存的 compose.keys 与本次显式 AURIGA_IAM_ENCRYPTION_KEY/AURIGA_WORKSPACE_ENCRYPTION_KEY 相容，再只读复用；忽略新的临时 proof 来源也不会修补旧材料。旧安装缺新增材料、proof/root/模板被改、fixture 或镜像摘要变化都无损拒绝，必须使用新的空安装材料目录，不允许删除 receipt、补根或覆盖同序发行。这里的序号 1 仅是隔离 M2 fixture；这些本地检查不代表真实 daemon、整栈 CI 或正式发行部署已验收。
`var/` 含应急凭据与本地测试私钥，不提交、不贴日志。仅将 `var/real-dsh.json` 和脱敏的 `var/w3-evidence.json` 交给主控；D0 独立处理 NAS 包，不运行任何 NAS 连接命令。

真实模式与 W2V 共用登录、独立 CookieJar、冷启动、实际 phase、Docker Running、edge 和双会话吊销检查，额外要求：

1. 以元数据中的精确不可变 `repo@M` 执行 `docker image inspect`，核对完整 RepoDigests 归属及真实 linux/amd64 平台。读取本次 `var/runtime-proofs/<manifesthex>/` 下原始 manifest/config，复用公开 collector 的严格校验，绑定 M 原字节、config descriptor 的 C/长度及 config 平台；生产 V 继续负责真实启动闭环。实际 Engine Id 只允许本次原 M 或 C，再固定这一个实际 Id，容器 `.Image` 与 `.Config.Image` 必须同时严格相等（兼容 Docker 27 的 C 与 Docker 29 的 M，拒绝混搭、名称/tag 和前缀）。容器内版本/锁摘要仍须与元数据一致；HTML 必须含真实 DSH boot 注入和 module 入口，假页或普通 200 HTML 不能通过。
2. 直接请求容器（绕开 edge）验证正式插件 health 字段白名单；无签名、错误签名、错主人、过期、重放和未签名健康写请求都必须为 `401 + common.unauthenticated`。正常签名必须取得真实 HTML。
3. real 模式必须指定 `RAW_HEARTBEAT_FILE`，从受控本机观察代理读取实际被 workspace 接受的心跳。先等待门锁正向请求的交互上报落稳，再持续至少65秒只访问免鉴权健康接口，要求每次健康请求都符合真实契约，至少两条实际心跳四计数均为0、health.ok=true、原始lastInteractionAt和平台lastActivityAt均不前进。心跳样本接收时间必须跨至少25秒，末条距窗口结束不超过35秒，防止开头突发请求或停止的发送器假通过。再经edge发真实用户页面请求，要求原始交互时间及平台投影同时前进；随后第二个65秒窗口再次核对实际心跳静态。全部成立后才记录rawHeartbeatVerified=true；这仍是HTTP用户交互验收，尚未覆盖完整浏览器前端操作。real模式不会代发心跳。
4. real 模式禁止脚本代发心跳；真实插件无法报活动则失败。真实闲置回收、闹钟唤醒仍必须分别同时取得 phase / Docker / edge 证据。WS 用 DSH 的 `/api/remote.mux` 原生传输，不要求假 echo；用 masked Pong 保活，并在 DELETE 紧前以唯一随机 Ping/Pong 往返证明传输仍可用。假模式在该位置重新完成文本回声。客户端持续读取控制帧，记录并回复 Close。edge 当前直接切断代理 TCP；若收到 DSH Close 帧、关闭早于或等于 DELETE 发出时间，都不能算吊销通过。

### 本机原始心跳观察

`deploy/compose/scripts/heartbeat-observer.mjs` 仅用于本机Linux测试，在宿主8082接收专用 edge DNS 身份的 mTLS 请求，经过固定回环8081及相同 CA、专用客户端证书和 `platform` DNS 校验转发至真实 combined。三类 API 在观察模式下保持同一 HTTPS origin，完整 Host 和入口 metadata 原样保留。它不合成请求、不改认证；只有真实workspace返回200才保存白名单字段：接收时间、实例UUID、四计数、交互时间、健康布尔值与版本。认证令牌只在内存原样转发，未知字段、health.problems和所有请求头都不落盘。报文最多64KiB，输出文件0600、必须是新文件，单次最多10000条。

使用上节公开步骤，在 prepare **之前**设置 `AURIGA_M2_HEARTBEAT_OBSERVER=1`。bootstrap 会生成观察器安装参数，并将三类 API 一起指向 `https://host.docker.internal:8082`，不手改 workspace upstream。观察进程必须在启动edge前运行：

```bash
cd deploy/compose
export RAW_HEARTBEAT_FILE="$PWD/var/raw-heartbeats.jsonl"
node scripts/heartbeat-observer.mjs &
OBSERVER_PID=$!
trap 'kill "$OBSERVER_PID" 2>/dev/null || true' EXIT
docker compose --env-file var/compose.env up -d
cd ../..
DSH_FIXTURE=real node e2e/m2.mjs
```

应在独立测试机运行，避免宿主8080/8081/8082/8084被其它服务占用；内部8083不发布。NAS配置不使用这个观察代理。输出与`w3-evidence.json`都是脱敏验收证据，原始var凭据文件不交付。生命周期所有严格检查结束后才将lifecycleVerified置true，任何提前失败都保留false。

## 端到端脚本（`e2e/m2.mjs`）严格验证了什么

Cookie：管理台 / 门户 / 实例各用独立 jar，按 Set-Cookie 的 host、Domain、Path、Max-Age/Expires 选择。除 jar 选择单测外，脚本还将实际门户、管理台会话 cookie 手动发给实例 Host，要求确切 `401 + edge.unauthorized`。库保留无过期属性的空值 cookie，拒绝 HTTP 源的 Secure、无效 `__Host-`、单标签 Domain，并忽略非法 Max-Age；它没有完整公共后缀列表，仅用于这里固定的 example.com Host，不是通用浏览器 cookie 实现。

顺序：

1. 应急账号登录管理台（Host=`admin.example.com:8084`、实际管理listener8084），登录事务须 completed、实际 `/me` 须 200
2. 将 workspace 策略 `idleMinutes` 调到契约下限 5
3. 签发入网令牌写入 `join/token`，等待节点出现在 `/admin/nodes`
4. 门户登录后 `POST /me/instance/open`，等到实际 `phase=running` 且 `ready`
5. `GET /open/<id>` 换票后访问实例 Host，断言假 DSH 响应（且不用管理台 cookie）。在原单次 HTTP 的 15 秒预算内，仅对 `503 + edge.instance_not_running` 有界重试，以等待实际 phase/Docker 就绪后的 NATS 路由投影；每次请求受剩余预算约束，鉴权失败、未知错误或非实例 HTML 立即失败，截止后仍失败。唤醒阶段同时受原有 480 秒总截止约束
6. 用实例令牌发全 0 心跳；写 `ops-cron/store.json` 闹钟；等待闲置回收与唤醒
   - **闲置成功**须同时成立：闲置窗口开始前，同一实例 jar 的 HTTP 为真实实例页且同一 Docker daemon 返回 `Running=true`；之后实际 `phase=stopped`（**不算**仅 `desired` 变化）、同名容器确实存在且 `Running=false`，同一 jar 经 edge 得到确切 `503 + edge.instance_not_running`。容器 missing、鉴权 401/403、其他错误均失败。真实用户 GET 会推进活动，因此不在闲置截止前追加 GET；停止后的具体路由错误又证明了 cookie 已通过鉴权。只在平台已明确 stopping/stopped 时容忍被拒的尾部假心跳。
   - **唤醒成功**须同时成立：实际 `phase=running` 且 `ready`、容器 `Running=true`，新 `State.StartedAt` 晚于本轮停止观察时刻，且不早于原闹钟减 120 秒预热期（允许 5 秒时钟容差）；到闹钟时刻后 `nextWakeAt` 被消费或前进，再经 edge 取得对应 fixture 的实例页。预热时间和 schedule 消费分别记证据；这不等于证明 DSH 执行了业务闹钟任务。沿用原 480 秒总截止，期间不调用 open 触发唤醒。
7. **双会话吊销**：先完成 A/B 两次登录，再让两者分别取得实例 HTTP + WebSocket。B 先做正向探测，A 紧挨 DELETE 再做同 cookie 的 HTTP 200 与 WS 往返；记录探测、DELETE 发出、关闭时间。B 经 `DELETE /api/iam/v1/me/sessions/{id}` 准确吊销 A；30 秒内 A 传输必须在 DELETE 之后关闭且无独立 DSH Close 帧，旧实例 cookie 的 HTTP 与新 WS 均须 401，A 门户 `/me` 须 401。B 的实例 HTTP、原 WS 往返、门户 `/me` 仍成功，B 会话列表不再列 A 且仍含当前 B。吊销接口须 200/204，**4xx 不算通过**。

任一步失败只打印步骤名、HTTP 状态、实例 phase/desired 等脱敏摘要（不打印 token/cookie/口令）。临时目录与 WebSocket 在结束时清理。

`safeSummary` 在截断前递归处理对象、数组和 JSON 字符串的凭据键，并对文本中的凭据赋值、Bearer 和 JWT 形态值脱敏。`e2e.yml` 在端到端脚本前执行 `node --test e2e/lib/*.test.mjs`，覆盖假阳性拒绝、嵌套脱敏、Cookie 边界、WS 握手/分片/扩展长度/Close 回应和假 DSH 缺失身份头拒绝。假 DSH 的升级始终校验与 HTTP 相同的身份头；普通健康 GET/HEAD 行为不变。

## 节点证书（serverAuth）

workspace NodeCa 签发节点证时带 **clientAuth + serverAuth**（E2）。edge 校验 serverAuth。

**E2 之前入网的旧节点证书缺 serverAuth，必须续期或重新入网，并重启 agent 入口。**

Compose 的 combined 使用 IAM 本地公开 JWKSource，issuer 与共享配置一致为完整 `http://portal.example.com:8080`，不再通过明文回环拉取 JWKS。HTTP-hop另用独立 `iam.crt`/`edge-iam.crt` 与正确 serverAuth/clientAuth、DNS SAN，原节点PKI不替代IAM身份。

fake-ip DNS 会让离线版 OIDC 的 SSRF 校验拒绝保留地址；应调整该 IdP 的 DNS 解析，不关闭校验。外部 IdP 仍依赖网络，细节见 [dsh-plugin.md](dsh-plugin.md#通用-oidc)。此限制不改变旧节点必须续期取得 serverAuth 的要求。

collab 沿 host network，以固定 issuer 的 `/oauth2/jwks` 经公开 edge HTTPS 取 IAM 公钥；纯 IP/127 指宿主。
必须先核部署 DNS/地址与公开端口可从宿主抵达 edge；不能因 URL 格式合法就视为可达。
进程仅在私有 tmpfs 导入已核浏览器公链的叶证书，保持主机名校验，不挂浏览器私钥、不改宿主/系统信任。
浏览器证书更换需显式重新准备此受信投影。此处的 TLS 信任不成为插件 network 根。

配置/receipt/权限局测不代表整栈通过。正式验收仍需父 PR 已合并后 merge main、精确 CI、非作者独审，
并由主控实跑 PG/独立 collab/edge/gateway、真实 loader 默认 provider 登录→register/ticket→keys/announcement→
WSS/受签 READY→断开后新票重连，以及错误 realm/根/过期公告拒绝。离线根按原 24 小时规则续发；
未配置 NetworkKeyPush 时公告主动广播仍 pending，不能声称全网撤销时限、SEND 或宿主会话收发已验。

## 已封 base 的首次 N1 激活

已有 base 安装不通过换 `-out` 或重新 prepare 带 collab 输入来升级。
首次激活写固定 `var/collab-activation` 和独立 receipt，保留 base receipt、身份/CA/runtime 根、
gateway secret、原 protocol.key 与全部封存配置逐字不变。运行时仅经固定 overlay 选择新投影。
只支持该 base 尚无 N1 激活、运维确认该 realm 尚无已发布历史的情况；不支持历史/next/轮换，不能删历史适配三 active。

激活先完整验证 base 封存、身份与元数据，再要求其已有唯一且精确的上述 `auriga-dsh` native client 登记。
缺失或漂移时在创建 activation 源、pending、锁前明确拒绝；不会补写旧 base 或重算 receipt。
旧无此客户端的 sealed base 不在本次首次 N1 闭环支持范围，没有自动迁移路径。
激活派生的 team properties 保留原固定客户端段，原 base 全部字节仍保持不变。

全新安装先按前文 **不传 collab-file** 准备 HTTPS base，保留同一 PG 卷与材料。
用真实 DNS/IP/证书启动 base 的 IAM/Org 与 edge，再以既有 first-party nativeConnect 流程真实登录。
未配置 network 的插件仍能完成身份登录，初次 register 不依赖 collab 或 network pin。
设备 access 必须为当前同租户 `ptyp=device/ctx=device` 且有 `auriga.connect.collab.use`；
不能用管理 cookie、内部服务票、AI token 或测试 SQL 伪造身份。
由受信 native OAuth 客户端准备 0600 的 `Authorization: Bearer …` 头文件，凭据不进 UI/模型/日志：

```bash
umask 077
curl --fail-with-body --silent --show-error --cacert "$HTTPS_TRUST_PEM" \
  --header @"$NATIVE_HEADER_FILE" --header 'Content-Type: application/json' \
  --data '{}' "$ISSUER/api/iam/v1/network/register" > "$BUNDLE/registration.json"
```

核返回 tenant/device 与已验设备身份一致，保留 realm/node/来源摘要。已有组织可用既有真实 register
结果或受控 IAM 只读查询核实；另一套数据库的相同数字不构成来源证明，realm=1 也不能据大小判断真假。
之后依 [离线密钥合同](../../contracts/network/key-operations.md) 审批三用途公钥及明确协议钥，
离线 `OfflineKeySigning sign` 生成根签对，再用同根/指纹 `install` 生成初始 state；
根私钥不交在线主机，minimumVersion 来自外部可信高水位，最长 24 小时不延长。
协议公钥须先获同 realm 根签批准，在线加载的 DER 私钥/kid/version/有效期逐项一致。
`collab-input.json` 格式仍用上节，各材料和独立指纹完整供应，不能手拼 state 或从首次 HTTP 响应自举根。

在激活前，DBA 在 **现有 PG 卷** 核对 collab owner/app/schema。
完全缺失时，可执行以下固定 M2 角色脚本（占位口令禁止用于生产）：

```bash
bash deploy/compose/scripts/compose.sh exec -T postgres \
  psql -X -v ON_ERROR_STOP=1 -U auriga_dev -d auriga \
  < deploy/compose/scripts/collab-roles.sql
```

若任一角色/schema 已存在，先核权限/口令与配置，再由 DBA 明确补齐，不能重置旧角色、DROP 或删卷。
独立 collab 启动使用原 Flyway：common + `db/collab` 由 owner 迁移，应用连接仅 app。
真 PG 验收须检查两张 Flyway 历史表成功、app 非 owner/owner 成员、非 SUPERUSER/BYPASSRLS、无 schema CREATE。
本地封存检查不能证明数据库已接纳。

先将以下两个摘要与受信安装记录独立核对，不以当前任意目录的自报值建立信任：

```bash
sha256sum deploy/compose/var/iam-installation/bootstrap.receipt
sha256sum deploy/compose/var/identity-keys.json
bash deploy/compose/scripts/activate-collab.sh \
  "$BUNDLE/collab-input.json" "$BASE_RECEIPT_SHA256" "$BASE_IDENTITY_SHA256"
bash deploy/compose/scripts/compose.sh up -d --build --wait
bash deploy/compose/scripts/compose.sh ps
```

脚本先只读验证 base 和输入，再明确停止 platform/edge/network/collab 并检查 Compose 的运行状态，
随后调用 Linux 激活入口；底层 `-stopped-confirmed` 是受信操作者的停服确认，不是 CLI 独立证明进程退出。
CLI 可用 `-activate-collab -out <base> -network-collab-file <input> -base-receipt-sha256 <hash>
-base-identity-sha256 <hash> -validate-access` 做只读预检；Windows 仅支持验证，不生成激活材料。

锁和 `.collab-activation.pending` 拒绝并发/半成品，最后原子提交独立目录；receipt 绑定 base 摘要、身份公钥摘要、
完整输入与全部新文件。重入只接受相同材料，不覆盖旧身份或隐式轮换。运行投影在
`var/collab-activation-runtime`，只有 state 子目录可写；独占锁不进入 source receipt。
`compose.sh` 每次启停/状态均用固定 Go 入口验封及 root 字节/元数据检查，再选择固定 activation overlay，
需要可用的锁定 Go 工具链/缓存及相应 root/sudo 权限。不能省略该统一入口后冒称激活检查已执行。
中断后不自动删除 lock/pending 或修复；先保留诊断。仅需安全停服时用 `compose.sh activation-stop`，
它只执行固定服务的 stop；`activation-running` 只列固定运行服务，两者不能启动未验证投影。
首次预检从独立摘要验封的 base access 取 Compose project，随后 stop、ps 和最终 config 均要求同一 project。
统一入口每次从原安装 receipt 完整验封的 `access.json` 的 edgeContainer 推导 project，
显式传 `--project-name` 并固定插值环境；外部 `COMPOSE_*` 选择变量清理后仅设置封存 project、固定 profile 和禁止自动 env-file。
原 `compose.env` 仍只作为固定 `--env-file` 输入，不被 shell source；不能通过 `-p`/`--project-name`、
`-f`（含紧凑形式）、env-file、profile 或 project-directory 参数改选。原安装验封失败时不调用 Docker。
中断后的 stop/ps 仍验证原 base，不要求独立 activation 已完成；别项目的空结果不能作为本 base 停服证明。
此绑定用于已有封存安装；尚无 `compose.env` 的首次 bootstrap-registry 沿原初装入口，不用于激活确认。
封存后若投影首次未完成，可在核实停服后重跑相同激活脚本；漂移/未知文件/链接/权限错配均拒绝。

`-check-collab-activation` 仅证明封存、base 身份与材料元数据一致，不等于 Java 根签/schema、PG 或真实 READY 已通过；
该只读检查可用于过期后诊断，密钥有效期仍由 Java/客户端原有硬截止强制执行。
实际验收还要核双服务票续发、真实 JWKS/TLS、loader 默认 provider 的受签 READY 与新票重连及负例。
首次激活入口不承担后续清单续发/轮换；已安装部署使用下节独立运维入口。

## 同部署 N1 密钥轮换（停机运维）

入口为 `scripts/rotate-collab-keys.sh publish|install|status <input.json>`。仅支持 Linux、原安装者为 root 的单签名器 Compose 安装；拒绝改变旧源目录的 owner 来适配此入口。需要受信的 Go 1.27.3、`/usr/bin/java`（JRE 25）、`/usr/bin/docker`、同机 `/var/run/docker.sock` 和原 PG。原安装/activation 已存在、原四个控制服务实例可检查且原 signer 留下了实际 `state.json.lock` 才能推进。Windows 不执行部署操作。此入口不接收 PG URL、租户、realm、root、SQL、命令、Compose recipe 或“PG proof”；全部从原封存材料和即时 PG 查询绑定。

每次发布均短暂停止 **edge/network/collab**。collab 持有业务 state 锁；network 是独立 protocol 私钥签名器；edge 在变更期间关闭对应公开入口。platform 只核同项目实例，不停止；PG/NATS、数据卷、身份、账号和设备不变。旧 signer 的整份 payload 在任何新版 PG 发布后都会被原 guard 拒绝，故每版都要安装同版 state 后再启动。这里没有私钥热切换或连续可用保证。

运行前从受信源码构建实际运维 jar，独立记录源码 HEAD 和 jar 摘要。部署入口固定 jar 路径及 `NetworkKeyOperator` main；不启动 Spring Web/Flyway。子进程使用固定空 loader 配置和空 Docker client 配置目录，Docker 固定本机 Unix socket。调用环境存在 `COMPOSE_*`、`DOCKER_*`、`LOADER_*`、`JAVA_TOOL_OPTIONS`、`JDK_JAVA_OPTIONS`、`_JAVA_OPTIONS`、`CLASSPATH` 覆盖时拒绝；在专门的干净运维进程运行，不改系统环境。

```sh
./mvnw -q -pl services/platform-app -am -DskipTests package
git rev-parse HEAD
sha256sum services/platform-app/target/platform-app-0.1.0-SNAPSHOT-exec.jar
sha256sum deploy/compose/var/iam-installation/bootstrap.receipt
sha256sum deploy/compose/var/identity-keys.json
```

在受保护的审批目录保存 `status-input.json`（替换三个独立核对的摘要；`privateFiles` 可省略）：

```json
{
  "baseReceiptSha256": "<64 lowercase hex>",
  "baseIdentitySha256": "<64 lowercase hex>",
  "operatorJarSha256": "<64 lowercase hex>"
}
```

目录 `0700`、文件 `0600`，属原 root 安装者；拒绝符号链接祖先、硬链接与暴露私钥。路径相对输入 JSON 所在目录解析。不得将根私钥放进仓库、在线主机、在线容器或运维输入；只提供离线根公钥，指纹/rootKid/realm/tenant/minimumVersion 均取原封存配置。

```sh
chmod 700 /secure/network-approval
chmod 600 /secure/network-approval/status-input.json
bash deploy/compose/scripts/rotate-collab-keys.sh status \
  /secure/network-approval/status-input.json > /secure/network-approval/before-status.json
```

status 对原 PG 权威行归档验根，返回 `version/databaseTime/manifestDigest/firstPublished/pendingPush`；过期旧 manifest 仍可归档检查。行缺失、低于原运行 state 或受信 floor、历史缺 kid/未来时间、错租户/根/realm、与已归档版本不同均拒绝，不将空库当初装。PG 仅保存最新完整 pair 和所有 kid 的首次公布 map，不自带逐版本归档。此前每个 ops 版本的原 pair 与状态快照由独立目录保留；后续查询还逐项比较首次公布检查点，不能用一份自填 JSON 代替真实查询。

例行轮换先离线审批完整 `next-payload.json`：版本必须高于真实 PG 高水位；所有旧 kid 的 alg/purpose/SPKI/notBefore/notAfter 原样，原 active 保留；新三用途 kid 只能 next。为了后续满足重叠，旧 active 必须覆盖拟激活 `issued_at + 360s`。清单最长 86400 秒，不能通过续清单延长叶钥。私钥按 kid 保存，不能覆盖原 business/protocol/management 文件。

在离线签名机使用同一受信构建的 jar 和既有根私钥，生成整对文件。该命令只在离线机执行，输出均为新文件：

```sh
java -Dloader.main=auriga.collab.network.keys.OfflineKeySigning \
  -cp /trusted/platform-app-0.1.0-SNAPSHOT-exec.jar \
  org.springframework.boot.loader.launch.PropertiesLauncher sign \
  /offline/next-payload.json offline-root /offline/root-private.der \
  /offline/next-signed.json /offline/next-announcement.json
```

`offline-root` 必须替换为原 rootKid，不能另建根。仅把公有 signed/announcement 和所需业务私钥安全交付给在线审批目录。`publish-input.json` 在 status 三个检查点之外加入：

```json
{
  "baseReceiptSha256": "<same base hash>",
  "baseIdentitySha256": "<same identity hash>",
  "operatorJarSha256": "<same jar hash>",
  "signedFile": "next-signed.json",
  "announcementFile": "next-announcement.json",
  "privateFiles": {}
}
```

```sh
chmod 600 /secure/network-approval/*.json
bash deploy/compose/scripts/rotate-collab-keys.sh publish \
  /secure/network-approval/publish-input.json
bash deploy/compose/scripts/rotate-collab-keys.sh status \
  /secure/network-approval/status-input.json > /secure/network-approval/next-pg-status.json
```

publish 先实际调用生产根签/schema/pair 校验；在租户 PG 事务内持既有 advisory lock，复读期望旧 pair 与真实 first_published，然后在回滚事务中预检生产 transition。通过后核同项目四实例的 labels/镜像/实际配置及原 state 挂载，再停止上述三服务，按同一实例 ID 复查 stopped/PID/restarting 和其它仍挂原 state/文件/祖先目录的容器。正式发布先取得原 state.lock，再在同锁事务内复核旧版本、首次公布记录和原 state 与封存/ops receipt 的字节摘要，然后调用生产 `NetworkKeyOperations.publish`，随后从 PG 复读确认；预检不是提交成功。应用连接必须无 superuser/BYPASSRLS/直接或继承的表 owner 权限。`pendingPush=true` 不能说已广播，PG 首次公布也不证明客户端收到 next。

普通 next 版可立即安装并恢复旧 active 的业务服务。`install-input.json` 使用同一完整 pair 和三个检查点，`privateFiles` 必须恰含全部 active+next kid（通常六把），例如 `"old-business":"old-business.der"`、`"next-business":"next-business.der"` 及其余两用途。retired/revoked 不保留私钥映射。先用真实 `SigningKeyLoader` 在隔离临时 state 验证全部私钥，再停机并使用**原实际 state 路径和原 `.lock`**安装同一 PG 版，完整加载/绑定原 signing guard。新 gateway PEM 的公钥、kid、版本、用途、active 状态及有效期都来自同一已验证清单；网关只得到 active protocol 私钥。

```sh
bash deploy/compose/scripts/rotate-collab-keys.sh install \
  /secure/network-approval/install-input.json
bash deploy/compose/scripts/compose.sh up -d
bash deploy/compose/scripts/compose.sh ps
```

轮换开始后，统一 lifecycle 支持 `up/start/stop/restart/down/ps/config` 和固定相关服务；不接受 exec/build、任意 recipe/project/选项或 `down -v`。新分支仍核原 base/activation 封存，但按 ops receipt 核新版 runtime/state，避免把旧初装副本比较误当升级成功。公开 pair 按完整目录提交，安装材料按版本只新增，两个 selector 文件均完成且 pending 消失后才可启动。原 base/activation receipt、原 v1、旧私钥源和源配置均不写。实际可写 state 是唯一原运行材料升级点。

current overlay 只改变 collab/network 的挂载。未变的 platform/edge 可以保留同一实例及其创建时的精确 base+activation（或 base+required）两文件标签；仍核 sealed project、working directory 和准确来源，不能接受任意旧 recipe。collab/network 必须符合当前 overlay 及同版安装挂载。下一次 publish/install 不要求重建 platform 或改容器标签。

不带服务名的 `stop/down` 会停止 PostgreSQL；`stop` 后用 `start` 或 `up -d`，`down` 后用 `up -d` 重建容器并复用原卷。`start` 保留 Compose 只启动已有容器的语义。`up/start/restart` 在本地安装、state、原锁、归档和 selector 检查通过后，内部仅恢复 PostgreSQL：固定同项目/recipe，`--no-deps --no-recreate --wait --wait-timeout 120`，无公开 postgres 服务选择器。原 `<sealed-project>_pgdata` 卷必须存在，核 local driver、项目/卷标签、实际路径及创建检查点；已有 PostgreSQL 容器还核原实例/镜像、recipe 和三处固定挂载，恢复后再复核。缺卷不会创建空库，实例/卷变化、启动或健康等待失败均停止；不会启动 platform/edge/network/collab 来探测 PG。随后仍执行真实 PG 权威状态、完整历史/版本、生产根签与 state 校验、active protocol 有效期检查，通过后才执行所请求的服务启动。PG 连接或权威检查失败时最多只留下已恢复的数据库依赖，签名服务继续停止；修正外部原因后可重复公开启动，无需删除 pending 或原 state.lock。未知轮换半提交仍按下文保留首失处理，不能套此依赖恢复旁路。

至少等待真实 PG first_published 满 86400 秒。first_published 由生产应用时钟写入 PG，不是数据库自动生成；主控仍须核实际应用/PG 时钟可信且未倒拨。该时间可能带亚秒，拟激活时间必须取 `ceil_to_second(max(firstPublished[newKid])+86400s)` 或更晚，且执行时真实时钟已达到它。例如对 status 的所有历史 kid 取最大值会更保守：

```sh
python3 - /secure/network-approval/next-pg-status.json <<'PY'
import json, sys
from datetime import datetime, timedelta
p = json.load(open(sys.argv[1], encoding="utf-8"))
a = max(datetime.fromisoformat(v.replace("Z", "+00:00"))
        for v in p["firstPublished"].values()) + timedelta(seconds=86400)
if a.microsecond:
    a = a.replace(microsecond=0) + timedelta(seconds=1)
print(a.isoformat().replace("+00:00", "Z"))
PY
```

成熟前再次运行 status，离线审批更高版本 active-payload：原 next->active、原 active->retired，保全部历史，issued_at 不早于该边界且旧 active 的原 notAfter 至少到 issued_at+360s。按同样离线 sign→publish→status→install→`compose.sh up -d` 操作；install 私钥映射移除 retired old，保留全部 active/next。原 `next` manifest 可能因最多24小时而先于 PG 成熟点到期；允许从其已验根的归档状态迁移。需要公钥连续可用时必须额外高版本续发相同 active+next，并再次安装同版 state；不能同版本变字节或回写 first_published。

恢复后重新只读 status，核精确部署/租户/realm/根/版本及三个用途有效时间。用原已授权设备、既有认证入口分别取 `/api/collab/v1/network/keys` 和 `/api/collab/v1/network/keys/announcement`，核返回完整 pair 与归档同版，另按原诊断流程核实际有效业务及 gateway protocol 签名。此入口不创建设备、账号、realm，不自动运行 READY，不关闭历史负例或未闭合 claims。公钥 GET、fanout、三用途实际签发与 READY 是各自的现场证据。

### expired-old 停机恢复

已过期 old 不能直接同版 retired+new active。最小流程是在真实 PG 当前高版之后，单独发布 **old active->retired + new next**，保全部原有效期；保持 edge/network/collab 停止，整个等待期不提供在线公钥 GET/业务签名，也不宣称 fanout。此最小入口不安装 next-only 的运行栈，install 会明确拒绝缺少有效 active 的版本。真实等待至少24小时（含亚秒向上取整）后，另签更高版本 **old 保持 retired + next->active**，再 publish/install/恢复。上一 PG 版已无 active，既有重叠规则没有可伪造的旧 active；仍完整执行根签、历史、真实 next 首发和新 active 有效期校验。没有泄露证据时不默认 revoked；revoked 永久硬拒历史封装。

### 中断与重入

`var/collab-operations/releases/<version>/publication.receipt` 和 `installs/<version>/install.receipt` 分别证明已提交 PG 发布与本地安装，不是改写初装 seal。`.lock/.pending` 独占本次实例；失败保留 `first-failure.json` 与阶段材料，未知或半完成不写完成回执、不自动回滚 PG/state、也不删除别的锁。PG 已提交而 selector 未完成时，旧 signer 已被原 guard fence，服务保持停止。必须保留首失供人工核查；此最小入口不会自动续跑部分提交，也不能删 pending 后盲重试。

中断期间仅保留 `compose.sh activation-stop` / `activation-running` 固定逃生入口：仍从 ops binding 校原封存、固定 project/本机 socket/recipe，前者仅停 edge/network/collab，后者仅列三服务 running ID，不启动、不改 PG/state。它们不通过旧 activation wrapper 的环境选择证明同项目。

只有已完整提交的同版本、同原始字节、同绑定、同 private 集合，且即时 PG 及原 runtime/state 全部相符时，重入才只读复用；同版本改一个字节、缺历史、降版本或改 private 都拒绝。原 signer `.lock` 是正常持久文件，安装使用 tryLock，绝不 unlink 绕锁。没有真实发布和24小时等待证据前，本节仅表示已实现的公开操作流程，不能写成现场轮换或 READY 已完成。
