# 构建与部署常见报错

本页按 `./auriga` 命令行的中文报错整理，格式是“报错原文 → 原因 → 怎么办”。命令行失败时输出以 `失败` 开头，后面是下表的原文。`%s` 等占位符表示实际文件名或数值。

部署后的问题先运行 `sudo ./auriga doctor`：它逐项输出 PASS/FAIL 和修复建议，输出不含凭据，可直接贴给现场的人。它不能替代用浏览器正常登录管理台实测。必备参数和需要保管的材料见[必备参数与保管清单](keep-list.zh.md)。

## 依赖与开发套件

### 改了依赖之后怎么出包

现场修改依赖锁文件后，离线套件里没有对应的新依赖。

- **构建机能联网，改的是 Go / Web / Java 依赖**：用 `./auriga bundle --build --online --sign-key <站点构建私钥> --out <安装包.tar>`。它只对锁变化的生态联网收集新增依赖，再断网构建，并打印、写入新增依赖清单（安装包里的 `site-dependencies.json`）。详见 `./auriga bundle --help`。
- **构建机不能联网，或改了系统包、Dockerfile 基础镜像**：目前仍需把变更发给维护方，由维护方出包含新依赖的套件（现场自制套件在后续版本提供）。
- **用站点配置管理依赖缓存**：服务器上的 `/etc/auriga/site.json` 与 `sudo ./auriga deps status|fetch|import` 见离线包 `README-OFFLINE.md` 的“站点配置与依赖缓存”一节。
- **deploy 失败看退出码和收据**：`auriga deploy` 退出码 1 表示没切换、现场未动，2 表示已自动回滚到上一版，3 表示需要人工；原因见 `/var/log/auriga/<时间>-deploy.json` 收据和同名日志，说明见 `README-OFFLINE.md` 的“本机部署”一节。

被算作依赖锁的文件按文件名判定，包括：`go.mod`、`go.sum`、`go.work`、`go.work.sum`、`pom.xml`、`package.json`、`package-lock.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`、`yarn.lock`、`bun.lock`、`uv.lock`、`poetry.lock`、`pyproject.toml`、`requirements.txt`、`*-requirements.txt`、`.npmrc`、`.nvmrc`、`.node-version`、`maven-wrapper.properties`、`maven.config`、`jvm.config`，以及名字以 `Dockerfile` 开头的文件。

向维护方申请新套件时请提供：

1. **报错原文**：完整的命令行输出，包括 `失败` 之后的全部内容、`devkit verify` 列出的“新增 / 缺失 / 不同”文件清单。
2. **改了哪些锁文件**：列出路径和改动内容（可附 `changes export` 导出的补丁，补丁与上述文件一起发）。
3. **源码版本**：`auriga-source.json` 里的上游版本和提交，以及现场版本号（`bundle` 输出或管理台“关于”页）。
4. 想新增或升级的依赖名称和版本，以及为什么需要。

`--offline` 构建的工具容器使用 `--network none --pull never`，缺依赖时报工具自己的具体错误。

### Windows 客户端：依赖锁与套件不一致

适用于 `auriga-client build`（桌面客户端发行），与上面服务端的 `bundle` 是两条独立流程。

- **改的是前端 / workspace 的 pnpm 依赖，或 dsh-plugin 的 npm 依赖，且构建机能联网**：用 `auriga-client build --online --devkit <发行签名套件目录> --verify-key <发行公钥> --site-devkit <新目录> ...`（其余参数同 `--offline`）。它只联网补变化的依赖，把发行套件（只读）派生为 `--site-devkit`，再断网构建；输出目录里的 `site-dependencies.json` 列出新增依赖，请签名前人工审阅。`--online` 与 `--offline` 互斥，`--site-devkit` 必须是本机固定磁盘上的全新目录。
- **改了 Node/Python/DSH/Java 版本、`.npmrc`、`packageManager`、`clients/installer/upstream.json` 或 Python/DSH 锁**：`--online` 一期不支持，请把变更发给维护方出新套件。

| 报错原文                                                                                                       | 原因                                                                                                                 | 怎么办                                                                                                                              |
| -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `签名输入发行依赖锁不匹配` 或 `Windows devkit 依赖锁不匹配，请准备对应锁摘要套件`                              | `--offline` 要求套件锁与源码完全一致，源码里的依赖锁被改过                                                           | 只是 pnpm / 插件 npm 依赖变化：改用 `build --online`；其他变化请联系维护方                                                          |
| `这类变化一期不支持，请联系维护方出新套件`，后跟文件列表                                                       | `--online` 只允许 pnpm 与 dsh-plugin 的 npm 依赖变化，列表里的文件超出范围                                           | 还原列表里的文件，或把变更发给维护方                                                                                                |
| `依赖锁与套件一致，无需联网补依赖：请直接使用 --offline`                                                       | 源码的依赖锁与发行套件完全相同                                                                                       | 去掉 `--online` / `--site-devkit`，改用 `--offline`                                                                                 |
| 离线构建报 `pnpm install --frozen-lockfile` 失败（锁与 package.json 不一致，`--online` 之后或 `--offline` 时） | 改的是依赖声明（dependencies 等），却没有更新 `web/pnpm-lock.yaml`。只改 scripts、version 等不影响依赖的字段不会触发 | 先在联网机运行 `pnpm install --lockfile-only` 更新锁文件，再用 `--online` 重试（用新的 `--site-devkit` 目录）                       |
| `--base-pnpm-lock 的摘要与基础套件记录…不符` 或 `无法读取 --base-pnpm-lock`                                    | 给的不是基础套件对应源码里的原始 `web/pnpm-lock.yaml`                                                                | 换成原始源码包里的文件；该参数只能与 `--online` 同用                                                                                |
| `复制后的派生套件与已校验的基础套件不一致`                                                                     | 复制期间基础套件被其他进程改动                                                                                       | 确认没有程序占用或修改基础套件，换新的 `--site-devkit` 重试                                                                         |
| `--site-devkit 必须是全新目录`                                                                                 | 目录已存在，或与基础套件、`--out` 互相包含                                                                           | 换一个本机固定磁盘上的新目录                                                                                                        |
| `--online 的基础套件必须是发行签名的，需要 --verify-key 或 --trust-fingerprint`                                | 联网派生必须先验基础套件的发行签名                                                                                   | 提供独立批准的发行公钥或指纹                                                                                                        |
| `输入准备命令失败（…）：…`（`--online` 过程中）                                                                | 联网取依赖失败，多半是网络或代理                                                                                     | 设置 `HTTPS_PROXY` / `HTTP_PROXY` / `NO_PROXY` 或 `npm_config_registry` 后换新的 `--site-devkit` 目录重试（失败时程序已清理半成品） |
| 警告：取不到基础套件对应的旧 `web/pnpm-lock.yaml`                                                              | 新增依赖清单无法与旧锁比对，“不再需要”数量显示为未知                                                                 | 用 `--base-pnpm-lock` 指向原始源码包里的 `web/pnpm-lock.yaml`，或人工核对锁文件的修改记录                                           |
| `套件需要更新的客户端发行脚本，请使用该套件发行页对应版本的源码`                                               | 套件清单用了当前脚本不认识的新能力（`requires`）                                                                     | 换用该套件发行页对应版本的源码和客户端脚本                                                                                          |

### Windows 客户端：重复构建与源码目录残留

`auriga-client build`（`--offline` 与 `--online`）不再向源码树写入：构建时把源码（不含 `node_modules`、`.git`、`target` 等）复制到 `<输出目录>\build-src`，在副本里安装依赖并构建，结束后（成功或失败）自动删除副本，所以同一份源码可以连续构建。源码身份、网络守卫、环境过滤、签名校验不变，校验对象仍是你给的源码目录。

| 报错原文                             | 原因                                                                                                                                                                                      | 处理                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `构建前发现预置生成内容：<路径>`     | 源码树里有 `node_modules`、`dist`、`.pnpm-store`（或基线未含的 `clients/dsh-plugin/ui`），多半是旧版本构建的残留。PowerShell 的 `Remove-Item` 会在 element-plus 的 `.pnpm` 超长路径上失败 | 运行 `.\scripts\client-release\auriga-client.cmd clean-source <源码目录>`（提示为 `ui` 时加 `--include-ui`）。它用 Node 删除，支持超长路径，只删这几类已知生成目录，遍历范围与构建前门禁一致（不进入 `.git`、`bin`、`data`、`target`、`deploy/compose/var`、`.dev` 等），不删其他文件；`ui` 属于签名基线或已被 Git 跟踪时拒绝 `--include-ui`；目录里没有 `scripts/client-release/build-node.json` 时拒绝执行。也可重新解压源码到全新目录 |
| 提示无法删除临时构建目录 `build-src` | 杀毒或其他进程占用                                                                                                                                                                        | 构建结果不受影响；稍后按提示用 Node 的 `rmSync` 删除，或直接删除整个输出目录的该子目录                                                                                                                                                                                                                                                                                                                                                   |

## 构建资源

| 报错原文                                                                                                               | 原因                                                                                       | 怎么办                                                                                                                                                     |
| ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `可用构建内存不足：Docker总内存…MiB，可用…MiB，至少需要…MiB（含保留给运行服务的1024MiB）；低峰重试或用独立Linux构建机` | 内存门禁。默认每个工具容器 4096 MiB，再预留 1024 MiB 给运行服务，可用内存须不少于 5120 MiB | 停掉不用的进程或低峰重试，或改用独立 Linux 构建机。可用 `--memory-mib`、`--cpus` 显式调整（下限 1024 MiB、1 CPU）。先用 `./auriga doctor --build` 单独检查 |
| `当前Linux Engine缺少内存/CPU配额控制，拒绝无保护构建；请使用支持cgroup限制的Engine或独立构建机`                       | Docker 不支持构建需要的 cgroup 限制                                                        | 换支持 cgroup 内存和 CPU 限制的 Engine，或用独立构建机                                                                                                     |
| `导出镜像（docker image save）失败：连续…没有读到任何数据…可调大 AURIGA_DOCKER_IMAGE_STALL_TIMEOUT`；或 `…总用时超过上限…`、`检查镜像（docker image inspect）超时…` | 现场负载高或磁盘慢，镜像导出/检查太慢。默认：导出开始出数据后连续 10 分钟无数据才中止（出第一个字节前只受总上限约束）、总上限 2 小时，检查 10 分钟 | 按报错里提示的变量调大后重试，取值为 Go 时长，范围 1m 到 24h：`AURIGA_DOCKER_IMAGE_STALL_TIMEOUT`（导出无进展）、`AURIGA_DOCKER_IMAGE_SAVE_MAX`（导出总上限）、`AURIGA_DOCKER_INSPECT_TIMEOUT`（检查），如 `AURIGA_DOCKER_IMAGE_STALL_TIMEOUT=30m ./auriga bundle --build …`。取值非法会在构建开始前报错。注意：导出镜像由开发套件 NAS 包里自带的引导程序执行，这些变量只对含本功能的套件生效；更早的套件仍是固定 3 分钟，只能换新套件或在机器空闲时重试 |
| `构建/安装只允许Linux本机Docker Unix socket；拒绝命名管道或远程TCP/SSH context，请选择本机Engine`                      | `DOCKER_HOST` 或 docker context 指向远程或命名管道                                         | 切回本机 Engine（取消 `DOCKER_HOST`，使用默认 context）                                                                                                    |

## 安装与升级

| `仍有运行容器写入数据目录，冷备份/恢复已中止`                                                                      | 备份时仍有容器挂着数据目录                                                        | 用 `sudo ./auriga stop` 停栈后再备份。`backup` 和 `upgrade` 正常会自己停栈，出现此报错说明有不受它管理的容器                                        |
| `资源密钥准备未完成，保留现有材料并处理错误` 或 `残缺或不安全的资源密钥权限 <名称>，保留材料并恢复属主/权限后重试` | 初始化资源密钥时被中断，或权限被改                                                | **不要删除已经使用的资源密钥**。从备份恢复，或把属主和权限改回提示的值。完整材料可原样复用                                                          |
| `服务健康等待超过五分钟，运行 ./auriga doctor 检查`                                                                | 启动后有服务没就绪                                                                | `sudo ./auriga doctor` 看哪项 FAIL，`sudo ./auriga logs` 看日志                                                                                     |
| 端口或网段冲突（Docker 或启动脚本给出的原文，不是 `auriga` 自己的固定文案）                                        | 8080/8084/8083 被占用，或默认网段 `192.0.2.0/26`、`192.0.2.128/26` 与现场网络重叠 | 安装器不改宿主路由、DNS 或防火墙。端口：换掉占用的程序。网段：保留错误输出和已有配置，交部署维护者选择不重叠的网段，走原有手工路径                  |
