# 消息网络部署后自动续期设计

状态：设计提案，审查等级 A（网络信任根），尚未实现、部署或完成独审。依据 main `7cbdcbf2bf75febd55d5669aa5173328e808fd19`，现场基线截至 2026-11-13。本文仅增加设计文档，不改变现行契约。

## 1. 目标、结论与依据

用户要求部署完成后不再人工周签，并已接受服务器持有运行密钥的风险。建议保留离线根，把清单签发权限定委托给消息网络运行签发者；平台自动更新清单、轮换业务钥、发布并让消费者采用新版本。运行签发者归 collab 域所有，合并部署时在 platform 进程内运行，独立部署时在 collab 运行，不让平台直接操作其他服务的表。

**一年期硬截止、根每次更换运行钥都必须人工签发、无限期无人值守，三者不能同时满足。** 服务器没有根或外部授权设施，就不能在一年后自行延长根授权。继续接受到期签名必须在根签授权中明确允许，不能靠消费者忽略到期时间实现。

推荐内部部署默认采用“无硬截止的运行授权 + 每年复核提醒”，每次真正更换运行钥仍由根签发；每日清单与短期业务钥继续硬截止。根只在初装、运行钥更换、撤销和灾难恢复时使用。这一方案改变了建议的一年硬有效期，须由用户决定 D1。另提供硬截止 365 天的严格配置，提前 30 天、7 天告警，到期只降级消息网络；它不满足无限期免维护，不作为推荐默认值。本文没有把该取舍冒充用户已批准。

## 2. 现状与事故

### 2.1 当前信任链

1. 每 realm 安装固定 Ed25519 根公钥和指纹；根无现行证书到期字段，根更换需受信安装。根私钥留在离线签名设施。
2. 根直接签完整 `SignedKeyset` 和 `KeysetAnnouncement`，分别使用 `Auriga.NetworkKeyset.v1\0` 和 `Auriga.NetworkKeysetAnnouncement.v1\0` 的域分离及 JCS。清单 `valid_until <= issued_at + 86400s`，重复下载不续期。公告绑定版本、清单摘要及截止时间。
3. 清单列三种独立业务钥：`business_delivery`、`protocol_response`、`management_state`。业务封装由对应 active 私钥签；业务钥本身作为清单条目受清单签名保护，并非另有独立根签证书。Java 对包括历史在内的业务钥寿命限制为 8 天，独立过期恢复新钥最多 7 天；现有 NAS 固定旧 operator JAR 是否具有 8 天规则须单独核验，不能从源码推断现场已升级。
4. 新业务钥先 next，PG 真实首发满 86400s 才 active，原 active 必须剩余至少 360s。kid、材料、用途、原期限不可改；retired/revoked 不可复活。业务封装通常另有短时效及 audience、epoch、nonce 等约束，清单续期不延长旧封装。
5. PG 记录最高版本、完整清单/公告、首发历史及 pending_push；本地安装 state、私钥、receipt 与 PG 绑定；客户端持久记录已见版本、公告 fence 和钥历史。PG 提交后旧本地状态不可继续签发。未接公告消费者时，pending/容器健康都不能证明全链送达。

### 2.2 两次事故的因果

2026-11-12：v47 清单过期，network/collab/broker 停止。小时巡检不会补签，核心服务升级不能恢复消息网络。恢复又碰到配方路径、镜像和容器定义绑定不一致，多次发布拒绝，恢复时间被拉长；最终单份根签 v48/v49 仅覆盖约一天，仍留下很窄的下一次激活窗口。B-NAS-UPGRADE-SHEET 的配方路径和固定 JAR 随包交付问题须随新迁移一起解决。

2026-11-13：定时执行因额度失败，v49 于 11:32:39Z 过期，旧 active 于 12:00Z 过期。next 虽已成熟，普通一步激活要求旧 active 剩余 360s，无法再通过；独立过期恢复又要求所有历史钥均过期，而 next 到 11-19 才到期。于是只能根签 v50（旧 active→retired）再根签 v51（next→active），最后另签周批。事故不是根算法失效，而是正常运行必须依赖人工/外部 AI 在窗口内完成签发、安装和恢复。

11-13 的恢复证据仅到 `SERVICES_READY announcement_verification=pending`、退出码 2，不能写成已验证真实客户端 READY。新方案验收必须补这一缺口。

安全必需的是信任锚独立安装、用途隔离、验签与期限、撤销不复活、单调版本、持久防回退及发布/签发互斥。离线根每份清单亲签、人工周批、固定 UTC 审批窗口、人工安装/启动是流程选择。24h 清单新鲜度和24h next 预告是现行安全策略：保留日常规则，但新增明确授权的自动恢复转换；不能冒称旧转换原样就能覆盖任意停机。

## 3. 新信任链与验证规则

### 3.1 根授权对象

新增 v2 严格受签对象，不把运行公钥塞进 v1 的 roots 充当根。Ed25519/JCS、无填充 base64url 和秒精度 UTC 沿用；新增各自独立签名域，具体字段在 K 线契约冻结。

- `RuntimeAuthority`：根签，绑定 tenant、realm、运行 kid/SPKI、唯一授权 ID、根控制序号 `authority_revision`、`not_before`、明确的到期策略、可选硬 `not_after`、复核提醒时间；能力仅包括清单/公告签发、三用途业务钥轮换、受限自动恢复及过期历史归档。声明清单最长24h、业务钥最长8天、禁止再委托、禁止签身份/发行/资源包或更换根。授权对象本身由根签名约束全部参数，部署配置只能进一步收紧。
- `RootControl`：根签的每 realm 累积授权/撤销快照，独立单调控制序号；撤销 ID/kid、替代授权和迁移最低版本。运行钥无权更改它。不能用 keyset_version 与控制序号比较大小。
- `SignedKeysetV2`：运行签完整 keyset，绑定授权摘要、控制序号、tenant/realm、版本、签发/截止、正常或恢复模式及历史归档边界；传输同时携带根授权和根控制对象。摘要覆盖完整 keyset 与授权引用，不能互换 tenant/realm 或拼装授权。
- `KeysetAnnouncementV2`：同一运行钥签，绑定上述授权引用、realm、版本、完整签名清单摘要和截止。公告只作 fence/刷新提示，不允许消息内自选 URL；控制快照另可根签分发，不依赖已被撤销的消息签发链。

运行钥不直接签业务消息；业务钥仍只签各自用途。没有通用 HTTP“签任意字节”接口。根签 CLI 仅保留授权、撤销、紧急恢复能力，日常清单只能由固定计划生成和签发。

### 3.2 消费者验证顺序

按安装根验 RootControl 及 RuntimeAuthority → 检查最高根控制序号、授权撤销、tenant/realm、能力、时间策略 → 验运行签名及域 → 检查公告/清单精确关联、最高版本及同版字节 → 检查业务钥不可变身份、状态、期限 → 原子持久化后放行业务。观察更高公告立即 fence，失败写盘不放行；到期/未知授权/缺链/越权/再委托均拒绝。硬期限模式的清单和新业务钥不得越过授权硬截止；无硬截止模式不能用“忽略 not_after”编码，必须是根签的显式枚举策略。

已安装的高控制序号始终优先于运行签的任意高版本；根撤销后该授权的所有清单、公告和业务钥均停止用于实时验签/签发，即使其原截止未到。根恢复可明确废弃被攻陷签发者制造的版本空间，以新的根控制代际及新清单序列起点替代；只有根能做此动作，运行钥不能重置计数。旧消息留存用于审计，不因撤销重新执行或重新签成“旧消息”。

**撤销传播边界**：消费端取得并持久安装根撤销快照后才能知道撤销。推荐模式没有在线根新鲜度服务，攻陷 NAS 的人可隐瞒撤销并用旧授权继续签新清单；不能宣称24h后全网必拒或5分钟全网撤销。事故止损必须经独立受信管理/安装渠道把根控制快照送达所有消费者，未确认者隔离。离线端再次联网须先同步控制快照再刷新清单；被控制的唯一路径无法保证送达。若要求有界全网撤销，另需独立在线根控制服务及硬新鲜度门禁，不在本方案虚构此能力。

### 3.3 谁需要改

- collab：`RootKeyPublication`、发布/签发器/安装器必须支持 v2、运行授权、自动恢复和在线原子换钥。
- network（ai-gateway）：目前网关协议签名器主要消费安装投影的 kid/版本/期限及私钥，并非完整根清单验签器。新增经根链验证的动态公钥/私钥快照装载，按同版原子热切换，旧快照立即 fence；不把它误写成只改根文件即可。
- broker 是构建自 NATS server 的服务，消费 broker.conf、TLS 材料与权限，不直接验业务 keyset。通常无需改 NATS 源码；其部署/鉴权接线应继续采用经核投影，不向它挂运行私钥。TLS CA 和服务凭据是另一条信任链，此次不续期它们，也不能承诺整个系统所有证书永久免维护。
- 节点代理的 NodeControl mTLS/发行信任链不变。节点上的 DSH 插件和测试探针若消费消息 keyset，必须升级 v2；不能将节点证书误当消息运行授权。
- 桌面端/托管及连接模式 DSH 使用的 `network/trust`、安装导出/导入、缓存和公告刷新都要改；桌面壳若不验消息签名，仅须确保发布时打包新版插件。上游 DSH 无需修改。旧插件不能验证新链，须先升级，不长期兼容 v1。

## 4. 自动运行与故障收敛

### 4.1 调度和日常换钥

进程启动即 reconcile，随后每分钟检查（带抖动），新清单寿命24h、每12h刷新一次，留下12h重试余量；不是等到每日截止才续签。版本按事务分配，实际 issued_at 取经校验的当前 UTC，不靠机器定时窗口预签。

三用途各一把 active，寿命不超过8天；建议每5天换一组，生成时立即以 next 发布，至少提前48h预告并确认真实首发满24h，正常激活时保留旧 active 360s验旧窗口。清单续签不改业务钥原期限。是否临近窗口由持久首发和截止计算，漏跑后重新算，不能只补跑最后一个 cron tick。每次轮换同时保留可用 active、成熟 next 和未过期 retired；网络积压的旧业务封装不因新清单获得新寿命。

### 4.2 多副本和半提交

以 `(tenant_id, realm)` 的 PG 行锁/事务咨询锁为唯一发布互斥，不使用 NAS 文件锁承担跨主机选主。沿用现有 PG 发布与业务签发互斥语义。候选的密文私钥、授权引用、期望前驱摘要、签名 pair、版本及发布 outbox 在一个短事务内提交；无外部网络调用、无 Docker 操作留在事务内。数据库断连/事务失败则不发布、不签发；重获锁后重读权威状态，不执行陈旧计划。唯一约束确保同版只有一组字节；同输入重入复用，不能重新生成同版不同签名/私钥。

每副本按提交版本加载并验证密文、根链及材料匹配，在进程内原子替换只读签发快照；每次签发仍核 PG 当前代际/版本，落后副本拒绝签并追平。网关私钥投影使用单独最小权限的本地投影器、目录原子替换和版本回执，跨主机通过既有受认证控制通道分发到固定节点路径。新节点无匹配私钥不承接流量；不能靠各副本本地生成不同 active。全部对外通路都具备新快照才报 READY；失败副本暂退流量，旧消息和 outbox 保留重试。

PG 成功而进程退出：下次从同一已提交 pair/密文重新加载；公告发送成功但确认丢失：允许重复发送，CAS 仅确认准确版本；投影安装半途断电：对照已提交版本/摘要重建或补回执，不回滚 PG、不删除 state.lock、不删首失。旧 `.pending` 迁移前须先按原流程恢复；新机制不在旧流程旁另开第二个签发者。自动续期不再需要 root + docker.sock 的小时 sidecar。

### 4.3 停机、时钟与无人工恢复

旧清单过期但业务 active 仍有效：直接签更高版清单并热装，不等待旧清单恢复有效。

active 过期而 next 已成熟且有效：v2 允许在同一事务将过期 active 置 retired、成熟 next 激活；只有尚有效旧 active 才需保留360s。此项明确替换旧“先退休再激活两份根签”的转换，仍保留真实 firstPublished。

所有可用钥都过期、next 未成熟或有效期限不足：使用根授权中受限的 `automatic_restart_recovery`，一次提交旧 active/next 全部 retired（revoked 保持）、三个全新 active、必要的 next，以及更高版有效清单；全新 active 寿命最多7天，firstPublished 是本次真实 PG 时间。无需等待全部历史钥过期，也不伪造24h成熟记录。与日常新增只能 next 的规则分开；恢复原因、旧截止、时钟证据、授权 ID 和前驱摘要进审计。这个应急能力使停机数周仍能自动恢复，也放弃了异常恢复时的24h预告等待；根授权必须显式包含它，消费者必须识别恢复模式。若授权被撤销或硬到期，则不得自动恢复。

PG 时钟为调度权威，应用与 PG 相差超过60s暂停新签发并告警，持续复测，偏差恢复后自动重试。记录最近权威时间高水位，明显回拨不生成低 issued_at；时间追平后自动恢复。消费者独立检查 UTC 和期限；不把容忍60s扩大成过期宽限。离线环境用本地可信时间源/RTC，不依赖公网 NTP；系统无法自行判断真实 UTC 时没有安全且保证可用的自动恢复，应明确报时钟异常，不偷偷调时或无限放宽期限。

### 4.4 历史增长是上线前置条件

现行清单 `keys.maxItems=128` 且 PG 要求保留所有历史，按每5天新增三把迟早耗尽，不能照搬后声称永久免维护。v2 传输只包含所有未到期钥和必要的撤销项，允许归档已到期至少360s且不再用于实时验证的条目；声明签名覆盖的归档截止与历史摘要。完整不可变材料/状态/首发与 kid/SPKI 唯一索引仍在 collab 审计历史中保存，禁止复用，不自动抹掉历史。

消费者维护已见钥的持久墓碑（身份摘要、原期限和终态），只在本地已知原期限满足归档边界时接受移出；缺少活跃/next/仍有效历史的快照拒绝。离线跨多版的客户端可直接验证根授权下的最新完整“当前可验钥集”，已有历史冲突仍拒绝，不要求逐版补齐已过期公钥。旧钥再出现须核墓碑且不得复活/改期限；全新客户端以受信根及最新控制代际建立初始历史，信任运行签发者这一点与首次清单一致。已过期消息不因归档重获验证资格，历史审计验签是单独只读模式。

服务器历史移到可分页的追加审计表，客户端墓碑独立于传输128把限制；存储增长按年测量并告警。加大128上限只能推迟故障，不算完成。跨语言应有超过128把/至少两年虚拟时间的持续轮换测试，此工作不得延期到自动续期上线以后。

## 5. 密钥保护、撤销与安全取舍

已有可复用的是 AES-256-GCM、随机96位 nonce、受保护部署 secret 和 tenant/purpose AAD 的模式（如 `services/iam/impl/.../Secrets.java`），不是现成全平台可跨服务调用的密钥库。collab 不依赖 IAM impl、不读取 IAM 表、不复用 IAM 的加密密钥；在自身域实现同样已采用的封装方式，必要公共抽取另走受保护路径审查。

运行私钥 PKCS8 DER 与新业务私钥存 collab 自有 PG 密文表；AAD 绑定 tenant、realm、kid、算法和用途，密文带 KEK ID；根授权/公钥可公开读取。独立 collab KEK 从部署 secret 文件装载，拟定 NAS 路径为 `${AURIGA_DATA_ROOT}/secrets/msgnet/kek`，容器内 `/run/secrets/msgnet-kek`，均为新设计路径。祖先目录禁止非受信写入，Linux 目录0700、文件0400/0600，Windows 当前服务账号显式私有 DACL（允许系统管理员），拒绝链接和权限不足；多副本通过同一受控 secret 分发机制共享 KEK。

仅 collab 签发进程的服务身份及宿主管理员可读 KEK/解密运行钥。网关只获本机 protocol 业务私钥，不获运行钥；broker、edge、普通 agent、租户管理员和 UI 不获运行钥/KEK。PG 运行角色按租户/RLS隔离，备份只含密文；KEK 备份须独立加密保管。宿主 root 或同进程任意执行可读内存/KEK，这不构成硬件隔离或抵御宿主入侵。

KEK 更换采用读旧新、写新、断点重加密、核全量完成再撤旧的步骤；当前 IAM `Secrets` 并无此密钥环，不能宣称已经具备。运行钥正常更换：提前生成新钥→根签新授权及控制修订→分发→先验证链再切签发→撤旧授权→核全部消费者采用。运行钥复核提醒到期不自动换钥；怀疑泄露立即换钥，不等提醒。

硬期限模式在30天、7天、1天阈值产生持久去重告警，重启跨过阈值补报；到期根授权不再合法，停止消息签发/连接就绪，保留登录、管理、模型等核心服务。推荐模式对年度复核做同样提醒，过期仅保持“需复核”告警，**每日清单和业务钥过期仍停止实时业务**。告警写管理台现有告警渠道、健康状态及结构化日志，离线环境须在正常管理页面可见，无外部通知配置不静默丢弃。

与现行流程相比，现行被攻陷 NAS 可盗业务钥、操纵本地状态，但不能自主根签任意未来清单；推荐方案被攻陷签发进程可在授权 realm 内持续造业务钥/清单、冒充三用途服务，直到独立根撤销控制送达并切断攻击者。其权限不能越到 IAM、软件发行或其他 realm，但同宿主攻陷可能另外拿到那些服务的秘密，不能声称实际入侵只影响消息。用户已接受“服务器持运行密钥”的总体取舍；无硬截止授权、自动恢复例外及撤销传播限制仍在 D1–D3 明示，未视作已接受。

止损：独立渠道停用受侵副本/隔离入口→保留审计证据→干净环境生成运行和业务钥、根签新控制代际并撤旧授权→向所有消费者安装撤销控制和最低代际→核旧授权即使签出更高版本也拒绝→重新上线并逐端确认。不能在受侵服务器上单纯重新加密旧钥就称恢复安全。

## 6. 首次部署体验与离线部署

新增一个公开安装命令入口（名称由 D 线冻结），内部按以下事务步骤执行，不把测试材料生成器当生产安装器：

1. 安装器本地生成运行钥、KEK 和部署请求，展示 realm、根指纹、运行用途及到期策略；已有根部署仅导出公钥请求，不读取真实根私钥。
2. 新部署可在受信安装机一次命令内生成根并签授权，或导入已有离线根签出的授权包。根私钥路径只交本机签名进程，不传私钥字节参数、不回显、不挂平台。根生成默认在安装机的私有输出目录，不能在 NAS 上生成后把“删除文件”冒称安全离线。
3. 签发根控制初版及运行授权；安装器验证根指纹、授权、私钥匹配、KEK权限和持久存储后一次提交，再由运行钥签首份清单和三把初始 active。输出公有安装包、秘密备份提示、正常入口及消息 READY 状态；重入只复用同一部署，不重生根。

因此“尽量一条命令”是受信安装机引导/签发的一条命令加目标端安装，或预签授权包的一条安装命令；根在另一离线机器时两端文件交接不可凭空消除。内网完全离线可用发行包、授权包和本地时间源完成，不依赖云端 CA、互联网或外部 AI 定时任务。对既有 NAS 必须用原根，不能为了快捷重建根。

根私钥在离线加密介质至少两份备份，恢复口令与介质分开，安装完成核一次可恢复性；NAS只留公钥。根丢失而运行授权未撤销：推荐模式仍可自动续期，但已失去根撤销/更换运行钥的能力，必须安排受信重新安装新根并逐端迁移。根和运行钥都丢失：无法仅靠公钥恢复原信任，需显式新根安装。KEK/数据库丢失同样依赖备份恢复或根授权重新签发；不得清空客户端账本伪装无事发生。

## 7. NAS 无中断迁移与旧流程退役

设计基线是 v51，有效至 2026-11-14T14:11:53Z；已批准队列 v52–v65 覆盖至 2026-11-21T12:00:00Z。这是历史现场快照，不是实施日当前状态；实施前只读重新核 PG、安装、队列、真实 READY 与控制链。按私有周批计划，v59 加 next、v62 激活；不能假定迁移时仍处于 v51。

1. 先完成 K/C/N/P/D 线、独审及必要验证；按 B-NAS-UPGRADE-SHEET 原配方路径升级包并带固定 operator JAR，验证摘要/权限，保留绑定/旧收据。新程序支持**一次性的 v1→v2 迁移导入**，不支持切换后常态双协议签发。
2. 在现有队列继续运行时先发布新版插件/桌面包、网关及 collab 消费能力。此阶段仍只发布 v1；核所有在线消费者具备 v2（真实 DSH、托管实例、连接客户端与探针），离线旧端下次必须升级。不满足则不切，旧机制照常续期；覆盖不足时仍由主控维护旧周批，设计完成不撤销既有保底任务。
3. 原根离线签运行授权与一次性迁移控制，绑定精确已核 v1 历史摘要/最高承诺版本和 v2 最低序列。获取旧续期锁和 PG 发布锁后冻结旧队列，确认没有在途发布；最高承诺包括所有已导入/已签发待交付版本，当前基线至少65，v2首版至少66，最终数值现场计算。移交全部业务私钥与首发历史、旧 next 状态及公告 fence，不改 kid/期限、不伪造成熟时间。
4. 新运行签发者提交首份 v2，与当前仍有效 active/协议私钥保持连续；先准备全部副本可用新快照，再切流量及公告。迁移屏障前失败继续旧队列，屏障后只向前补装/恢复，禁止重新开旧队列。根签的最低代际防被重放的未来 v1周批覆盖 v2；不能仅删除队列文件。
5. 从正常登录后的终端/设备页面确认连接 READY，并以两台真实 DSH 完成发送、接收、回执和重连；核三用途签名、公告实际消费与重启自动续期。容器 healthy、内部 GET 和源码都不足以验收。实施由主控串行操作 NAS，本工位不执行。

“不中断”依赖新旧有效 active 的重叠、先升级消费者、原子热切换和多副本流量切换。现有停签/重启安装无法单凭脚本保证零中断，故热切换是上线前置；消息耐久、重连后自动追平必须验证，不能把仅“不丢数据”冒充连接从未重连。无法滚动的单机进程升级需提前说明可见重连，不能许诺单进程重启零断连。

切换核验后从公开产品删除 queue-prepare/export/import、单份请求 prepare/根签发布、固定 UTC 周批窗口、人工 approval、周签审阅/确认脚本和 root+docker.sock collab-renew loop，以及对应 compose profile、配置、测试及手册常态流程。根 CLI 保留授权/撤销/紧急恢复；只读历史核验、status、审计导出、pending 完整性诊断保留。已有 requests/batches/queues/releases/receipts 仅只读封存，不删除现场证据；旧命令明确拒绝已迁移环境。主控取消旧周签/检查定时任务并确认无第二写者。

现行分阶段过期恢复、等待全部历史过期的人工恢复从新日常运维删除，替换为第4.3节自动恢复；根紧急恢复保留用于运行钥撤销、硬到期、遗失或数据灾难。DB/文件被篡改、无法验证的 pending 不盲自动采纳，继续消息降级并报告准确原因，核心服务仍可用。升级/回滚均不得改旧收据或清空 PG；v2切换后的旧二进制回滚必须拒绝消息签发，核心回滚独立处理。

## 10. 待用户决定

- **D1 运行授权期限**：推荐无硬截止、365天复核提醒，运行钥更换由根签；满足无限期免周签/年签。备选365天硬截止可配置，30/7/1天提醒，到期消息停止；这意味着年度人工维护。若坚持硬365天且永远无人维护，须改为独立在线根授权服务或根允许运行钥自续/再委托，两者扩大另一层在线权限及复杂度，不推荐默默引入。
- **D2 自动恢复权限**：推荐根明确允许第4.3节受限恢复，过期active无需旧360s窗口，极端停机允许新active免24h预告，保留全部审计与防回退。理由是任意长停机后自主恢复需要此例外；拒绝它就不能保证“部署后不用管”。
- **D3 撤销送达与安全边界**：推荐接受独立受信分发并逐端确认的撤销模型，无全网固定时限承诺；失联端隔离。若要求强制有界撤销，需另建独立在线根控制新鲜度服务，会增加部署和离线可用性约束。
- **D4 业务时序与历史**：推荐24h清单、12h刷新、每分钟检查，业务钥最长8天、5天换代、48h预告，并上线前完成历史归档/墓碑；保留现有安全时序同时留出重试余量。配置允许收紧，不允许超过根授权上限。
- **D5 切换客户端策略**：推荐所有受管理在线端先升级再切v2，旧离线端回归时先升级；不保留长期v1兼容。单机升级允许短暂自动重连但不丢耐久消息；要求连接也绝不断须采用滚动副本部署并验证流量切换。
