# Auriga 管理台需求完整性复核

复核日期：2026-10-23。范围：本轮用户已确认的产品需求、当前管理台/插件原型、旧 dsh-team-hub 管理前端、Auriga 架构和公开接口契约。本文是设计审查与建议，不把建议视为用户已确认的需求，也不评定所有后端服务的实现完成度。

## 判断

现有八组导航能够容纳当前管理需求，可以继续使用。资源使用、DSH 设置、总部 DSH、云端管理台的分工已经明确。

但管理台尚不具备完整的业务操作流程。当前原型中，资源审核/发布与部分实例操作有模拟交互；许多配置、授权、接入、运维页面只有列表或说明。尤其缺少资源发布后的分发追踪、现场接入凭据管理、云端工具托管管理，以及总部 DSH 的真实访问与运行流程。

应区分三层证据：

- **设计**：本目录 HTML 及 README 表达产品方案；按钮、示例状态与浏览器持久化不证明服务端能力存在。
- **接口契约**：OpenAPI 与 README 定义允许怎样实现；有接口不等于已部署可用。
- **现有管理前端**：本次读取的 `web/admin/src/router.ts` 有登录、成员列表；分组、角色、身份源、设置仍路由到 PlaceholderView。`MembersView.vue` 接入成员查询、搜索和分页。它与本目录多模块原型的覆盖范围明显不同，不能以原型推断正式管理台完成度。

不建议给出“完成了百分之多少”：模块粒度、接口实现、真实运行验证并不一致，百分比会掩盖关键缺口。

## 已确认的范围

1. 同一个 Auriga 插件用于云端与现场 DSH；宿主侧栏一个 Auriga 卡槽，右侧资源市场/我的资源两个页签。
2. 个人私有资源在当前 DSH 使用；共享资源由总部审核与发布。公开市场面向 Auriga 用户，界面不强调团队切换。
3. Skills、插件安装；工具打开独立子页，支持云端和本地位置。
4. DSH 统一设置弹窗承载插件设置；原账号、安全与连接功能要有迁移归属。
5. 总部 Agent 是独立的系统 DSH；管理员从管理台进入并主动聊天、发起任务。对话、任务、报告不再另做管理台业务页面。
6. 云端管理台保留中转站、Auto 模型选择等总部管理能力。
7. 当前不加入个人记忆、公共知识管理或用户定时任务编辑。备份与运行时唤醒等平台调度不等同于用户定时任务。

## 逐项复核

### F01 资源审核、发布与分发：有主流程，缺发布后的治理

**已有**：审核队列、已发布资源、等级说明；模拟审核/驳回、发布、普通下架，禁止作者自审/自发。

**需要补齐**：固定版本的审核对象、版本差异、包校验结果、可见范围和目标范围；发布失败后的状态及重新处理；发布版本历史；目标实例已安装版本、待更新版本、分发进度、失败原因、重试；普通下架与恶意撤销的不同结果。回退必须明确版本、目标与授权，不能视为简单修改 latest。

**管理边界**：管理员治理共享资源和受管分发，不默认浏览全部个人私有内容；L4 私有签名与共享送审也要分开。审核通过、签发发布、节点应用三种状态分别显示。

**位置建议**：现有“已发布资源”详情增加版本/发布/分发记录；“分发策略”补真实目标与结果。无须新增一级菜单。

**优先级**：资源市场首发必需。Skills、工具的安装/托管规则需先补契约。

**依据**：[资源契约](../../../contracts/resource/README.md)；[资源接口](../../../contracts/openapi/resource.yaml) 的审核、发布、分发与降级授权操作；当前 `prototype.js` 的 `resourcesPage`、`resourceDetail`。

### F02 云端工具托管：有资源类型，没有完整管理面

**已有**：插件工具子页、云端/本地选择、工具审核示例。

**需要补齐**：哪些工具已经部署、部署版本、负责人、访问范围、可用地址、部署/构建结果、失败日志、存储占用、暂停/恢复/回退。审核发布状态和部署就绪状态独立：通过审核并不代表云端工具可以打开。

**先明确边界**：本轮需求首先是简单前端工具，可按静态 HTML/JS 制品设计；不要未经确认扩展成任意服务端程序托管平台。工具使用独立来源或隔离页面，访问用户数据要另行授权。

**本地工具**：总部只看到经授权上报的元数据或用户提交的共享制品，不把现场工具当成总部应用远程部署。将本地工具发布到市场时上传云端副本，仍是待确认的具体产品方案。

**位置建议**：“资源治理”增加“工具托管”子页，或工具详情中的“部署”页签。

**优先级**：若首发承诺云端工具，属于首发必需；否则需明确暂缓该承诺。

**依据**：[插件设计](../auriga-plugin/README.md)；当前资源首批契约只覆盖 plugin。

### F03 现场接入与凭据：最明显的管理缺口之一

**已有**：现场终端列表、连接状态、插件版本；插件设置有总部 URL＋Key。

**需要补齐**：Key 从哪里获得、归属谁、可做什么、何时过期、能否绑定多个终端、如何轮换/吊销、终端遗失如何断开；显示 DSH/插件/前端版本与兼容状态。设备授权失败、凭据过期与总部不可达要能区分。

**关键设计问题**：用户界面称为“Key”不等于必须使用长期通用 API Key。需明确它是一次性接入材料、设备凭据还是其他凭据，并与 Auriga 设备登录及令牌契约映射。模型 API Key、节点加入令牌、现场插件凭据分别管理，不能只做一个无用途区分的“密钥列表”。

**位置建议**：“运行环境 → 现场终端”负责设备绑定/接入/吊销；需要独立凭据列表时放“安全与接入 → 接入凭据”，终端详情链接到它，避免重复管理。

**优先级**：现场接入首发必需。

**依据**：旧 Hub `admin.js/loadDevices` 已有一次性接入码与设备吊销；[IAM 接口](../../../contracts/openapi/iam.yaml) 的设备流程；[插件设置](../auriga-plugin/README.md)。旧接入码仅作迁移参考，不假定等于新 Key。

### F04 总部 Agent：身份边界已定，运行与进入还需落地

**已有**：首页快捷入口与独立总部页，说明系统 DSH、总部工作区、当前操作管理员。

**需要补齐**：首次配置/创建系统实例、绑定独立工作区、选择运行节点与配额、常驻策略、默认模型、总部预设/工具权限、进入授权；未启动、启动中、就绪、不可达等完整状态。允许访问的管理员及多人并发规则需要确定。

**不能漏掉的依赖**：管理台进入总部 DSH 的授权交接、实际操作人审计、总部调用 Auto 的系统身份。不能使用“打开我的实例”接口代替总部入口，不能在 URL 里附带系统长期凭据。

**保留运行治理**：任务聊天移到 DSH 后，Agent 通讯连接是否正常、是否因策略被禁止、发生错误如何定位仍属于运行诊断。可在总部详情与终端详情中显示连接与错误元数据，不恢复对话正文浏览器或任务调度页面。

**迁移问题**：旧总部会话、任务报告、正在执行的任务如何保留/继续，需要单独迁移方案；取消旧管理台页面不等于丢弃历史。

**优先级**：总部 Agent 首发必需。

**依据**：本轮用户决定；旧 `team-agents-design.zh.md` 第 6 节；当前 `headquarters.js`；[Workspace 接口](../../../contracts/openapi/workspace.yaml) 的 `openMyInstance` 是本人入口；[平台架构](../../architecture/platform.zh.md) 原 managed 门锁按实例主人授权，系统实例多人访问须明确适配。

### F05 模型中转站与 Auto：展示较全，配置和授权尚不全

**已有**：中转站、提供商分组、Auto 策略/模型池模拟、用量维度、API Key 列表和签发说明。

**需要补齐**：提供商创建/编辑/启停、上游凭据轮换与撤销、获取并导入模型、模型字段编辑、模型可调用范围、测试错误；API Key 实际签发/吊销/到期流程；日期范围、用量明细、预算生效与超额状态。总部模型用量与管理员个人调用需明确归属。

**能力区分**：当前 Auto 是顺序优先/轮询/故障切换，不是按任务内容自动判断最合适模型。若未来需要语义选模，应作为另一个需求。

**契约差异**：旧 Hub Auto、图片和外部 API Key 不属于 Auriga G1 当前承诺；G1 不自动重试/故障切换，系统身份也不能直接照搬旧 Hub。旧 Hub `0=不限` 与 G1 `0=禁止` 需显式映射。提供商获取模型/测试也不可仅据原型按钮断言当前 Auriga 管理 API 已有对应操作。

**位置建议**：保持现有五个子页，完善详情和表单。

**优先级**：中转站核心配置为首发必需；Auto 与外部客户端 Key 是用户明确要保留的范围，需列入迁移，不得静默删掉。

**依据**：旧 `policy-ui.js`；[AI 接口](../../../contracts/openapi/ai.yaml) 的凭据生命周期与模型 grants；[AI 契约](../../../contracts/ai/README.md)。

### F06 成员、分组、授权与账号恢复：菜单齐全，操作较薄

**已有**：成员、邀请列表与模拟邀请；角色/分组说明卡。

**需要补齐**：成员启停、角色授予/收回、分组增删及成员调整、邀请撤销/到期/使用情况、单个成员有效权限与配额、身份绑定、账号恢复、MFA 重置、会话撤销。重要的是管理员能解释“这个人为什么有/没有某权限”。

**角色建议**：权限集合支持细分，但首发可只提供少量固定角色。原型把所有模型管理固定为超管只是演示选择，不等于已确认的最终权限政策；总部 DSH 访问也应是显式权限。

**离职**：账号停用、会话/设备/Key 失效、实例停止、资源交接、数据保留、复职/恢复、到期清理应组成可追踪流程。

**位置建议**：成员详情承担账号与授权操作；离职处置在成员详情发起，“平台运维 → 成员离职”汇总待办，两处复用同一状态。

**优先级**：基本成员授权、账号恢复和失效处理为首发必需；复杂自定义角色编辑可后续补。

**依据**：旧 `admin.js/renderMemberOps`；[Org 接口](../../../contracts/openapi/org.yaml) 的角色绑定、邀请、配额与离职；[IAM 接口](../../../contracts/openapi/iam.yaml) 的账号会话、身份解除与 MFA 重置。

### F07 配额与策略：缺“实际生效值”视角

**已有**：系统设置中的默认实例配额、闲置回收说明；Auto 示例 Token 上限。

**需要补齐**：默认/分组/个人覆盖及有效结果；CPU、内存、磁盘、实例数量、模型预算等不同配额各自生效范围；已使用、已预留、剩余、超额处理。策略也要显示来源与作用对象，如私有插件、资源可见范围、模型调用和出网规则。

**位置建议**：默认规则放系统设置，分组/个人覆盖放成员与权限，实际用量放对应运行/模型页面，链接互通，不做三套互相冲突的编辑器。

**优先级**：首发至少提供默认值、个人有效结果和超限提示；分组高级覆盖可分阶段。

**依据**：[Org 接口](../../../contracts/openapi/org.yaml) 的 default/group/member/effective quota 与 policy；[AI 契约](../../../contracts/ai/README.md) 的预占预算。

### F08 实例与节点管理：缺加入、配置和变更结果

**已有**：成员实例启停模拟、期望/观察版本；节点与终端分列。

**需要补齐**：节点加入材料、加入进度、驱动和版本兼容、禁用调度/排空/退役、容量不足；实例规格修改、重启、失败原因、常驻与闲置策略、运行时版本选择。升级是否需要重启、影响哪些实例、何时完成需可查看。

**管理边界**：查看运行元数据不自动授予进入成员个人 DSH 或文件系统的权限；总部 DSH 的访问入口不是通用管理员代登功能。

**位置建议**：运行环境详情和页内操作；升级与版本发布统一归平台运维。

**优先级**：单节点首发仍需加入/失效/基本配置；批量排空和灰度可以后续完善。

**依据**：[Workspace 接口](../../../contracts/openapi/workspace.yaml) 已定义 updateInstance、join tokens、drainNode、runtime/default；[节点架构](../../architecture/node-agent.zh.md)。接口定义不证明执行链已验收。

### F09 插件前端与运行时版本：尚未支撑“总部更新，现场少升级”的核心目标

**已有**：插件设置分别显示插件版本和界面版本；系统设置只有运行时版本说明卡。

**需要补齐**：当前前端包、兼容的插件/协议版本、发布批次、目标范围、各终端已用版本、更新失败、回退/暂停发布。前端更新不兼容时保留可用版本并提示需要升级插件；新增本地能力仍可能要求更新插件。

**分开看三类版本**：Auriga 插件版本、可独立更新的前端包、DSH/节点运行时版本。不能用“升级平台”一个按钮代替三类不同动作。

**位置建议**：“平台运维 → 版本与升级”；发布也可以由既有部署流程完成，管理台首发至少可读地显示版本、兼容关系及失败结果，不必做浏览器上传任意运行代码。

**优先级**：版本识别、兼容判定和失败回退为首发基础；完整灰度发布 UI 可后续。

**依据**：用户关于现场频繁更新的要求；[平台架构](../../architecture/platform.zh.md) 的插件/面板协议版本与签名面板包；[插件设计](../auriga-plugin/README.md)。

### F10 运维、备份、通知与审计：有摘要，缺处置结果

**已有**：两条示例异常、备份列表、离职示例、审计列表。

**需要补齐**：异常详情、影响对象、首次/最近发生、确认/解决/恢复、关联运行日志；备份范围、保存位置状态、失败重试、恢复目标和验证；审计按时间/人/对象/事件/结果检索，前后变更和请求关联标识。

**旧 Hub 遗漏项**：通知公告。旧 `operations-ui.js` 有按全体/分组/成员发布、已发历史和收件箱；当前只有“通知渠道”卡片。资源驳回、接入过期、维护和升级失败都需要可达的反馈渠道。首发可做站内通知与关键结果，不必同时接齐邮件、IM、Webhook。

**备份范围**：平台配置/数据库、资源包、成员卷、总部工作区应分别说明；显示“备份成功”不足以承诺全部可恢复。管理台恢复动作依赖外部部署/存储策略，不宜把所有底层操作都搬进页面。

**位置建议**：平台运维中补通知公告与处置详情；审计维持独立入口。

**优先级**：关键失败可诊断、通知可达、备份可验证和审计可追踪为上线基础；高级外部渠道、报表可后续。

### F11 身份源、出网与管理员自身安全：不能停留在状态卡

**已有**：内置/OIDC/应急身份源卡片、只读访问入口、出网策略说明。

**需要补齐**：身份源配置、测试、启停、排序与绑定影响；应急入口状态和必要恢复流程；管理员自身账号、安全设置、当前会话和退出入口。出网规则需要分类、目标、例外、生效范围及拒绝原因，而非只显示“白名单”。

**位置建议**：身份源与出网规则保留在安全与接入；管理员自己的安全与退出在头像菜单。域名、反向代理、数据库等底层部署配置仍可由安装器/ctl 管，管理台显示有效配置即可。

**优先级**：登录、退出、会话失效、身份源故障恢复属于首发；更广泛外部连接器可后续。

**依据**：[身份架构](../../architecture/identity.zh.md)；[IAM 接口](../../../contracts/openapi/iam.yaml)；旧 Hub 分类出网设计；当前原型头像菜单只是角色预览。

### F12 所有页面共用的交互：需要完整状态与操作反馈

当前静态示例没有覆盖真实请求的加载、无数据、服务不可达、权限变化、操作冲突、提交中、部分失败与重试；列表分页主要是单页示意。多管理员同时审核、角色撤销后仍停留旧页面、编辑未保存离开、后台任务提交后刷新，都需要明确处理。

建议统一管理操作结果：已提交 → 执行中 → 成功/失败，显示影响对象与实际结果；进入 DSH 不应自动发送任务。普通资源下架、成员停用、节点排空各自明确影响，不能全部套成“保存成功”。

这是操作流程完整性问题，不需要新一级菜单。原型中的“角色预览”“模拟节点回报”“选模模拟”等控件不进入正式产品。

## 当前必须先定清楚的产品边界

### 公开市场的实际范围

用户已确认面向所有 Auriga 用户、界面不强调团队。当前部署只有一个团队时，可先按该平台部署内所有获授权用户理解；是否还要跨独立 Auriga 部署的全球共享，需要另行确认，不能自动扩大。当前资源契约按 tenant 授权；UI 不显示租户切换不等于取消服务端隔离。

### 离线“本地可用”的范围

独立本地资源、平台签名受管资源、云端工具分别说明。平台签名受管资源受到撤销清单有效期限制，资源契约规定清单失效后停止含受管资源的实例，不能承诺这类资源断网后无限运行。纯本地资源是否受同一约束要按运行模式和安装来源明确，避免给用户一个覆盖所有资源的离线承诺。

### 总部 Agent 能力与管理权

“管理员进入总部 DSH”已确认，但进入权限、Agent 工具权限、模型调用身份和资源授权不能混成一个超管权限。先确定系统实例归属与访问授权，再实现入口；不以一个跳转按钮代替这条业务链。

### 原型与旧架构的优先关系

用户取消公共知识、暂缓记忆和用户定时任务、迁移总部对话界面等最新决定优先。历史文档中仍列出的 knowledge 服务或管理台任务页，不自动成为本轮必做界面。需在实施计划中同步范围，避免后续工人按旧设计补回已删除页面。

## 导航建议

保持八个主入口，补页签/详情即可：

1. 概览：待办、健康、总部 DSH 入口、重要通知。
2. 资源治理：审核、已发布、分发、工具托管。
3. 成员与权限：成员、邀请、分组、角色；详情承载恢复、授权和有效配额。
4. 运行环境：成员实例、现场终端、节点、总部 Agent。
5. 模型与用量：中转站、提供商与模型、Auto、用量、模型 API Key。
6. 安全与接入：身份源、插件接入凭据、访问入口、出网规则。
7. 平台运维：异常、版本与升级、备份恢复、离职处置、通知公告、系统设置。低频设置可折叠，避免横向页签过多。
8. 审计日志：按人、时间、对象和结果查找。

不新增聊天中心、任务中心、个人文件/记忆后台、公共知识后台或用户定时任务编辑器。项目共享空间、环境模板、更多第三方集成属于历史远期方向，本轮无新增确认，不作为首发缺陷。复杂商业计费、许可证运营也不应因一个说明卡片而扩大当前范围。

## 建议按完整使用流程补设计

### 第一批：直接决定当前产品是否可用

- 成员加入/登录 → 配置现场接入 → 成功使用资源市场 → 失效或吊销后正确反馈。
- 作者送审 → 驳回修改或通过 → 固定版本发布 → 插件安装/更新 → 管理员查到分发结果 → 下架/撤销有明确效果。
- 云端工具提交 → 审核 → 托管就绪 → 用户独立打开 → 部署失败/暂停/版本恢复。
- 管理员进入总部系统 DSH → 主动聊天 → 总部以授权模型和工具执行 → 结果保留在总部会话，操作人可追踪。
- 提供商配置 → 获取/配置模型 → 调用授权 → Auto 或显式模型 → 用量与预算 → 凭据轮换/吊销。

### 第二批：日常运行必需

成员授权与账号恢复、默认及有效配额、实例规格/生命周期、节点接入与诊断、版本兼容和更新失败处理、通知、备份验证、离职与审计。正式上线前仍须有可执行流程；不一定每项都要复杂网页编辑器，可以明确复用受控部署/运维入口。

### 后续增强

多批灰度、批量迁移、复杂角色编辑、更多通知渠道、详细经营报表。不要在核心流程尚未贯通时继续堆菜单。

## 下一轮设计验收方式

以真实场景串起来检查，而不是按“有没有页面”计数：

1. 新成员如何从邀请到现场接入，并找回失效的账号？
2. 新资源如何从本地创建到共享发布，再安装到云端与现场？
3. 某次更新失败或某个版本被撤销，管理员在哪里看影响和处理结果？
4. 云端工具通过审核却没有部署成功，作者与管理员分别看到什么？
5. 两位管理员先后进入总部 DSH，是否保持总部身份并区分实际操作人？
6. Auto 首选失败、池全部不可用、预算耗尽，各如何展示和追踪？
7. 总部升级前端包后，现场无需升级插件的条件、失败与回退如何体现？
8. 员工离职、终端遗失、节点离线、恢复备份，能否从触发到最终结果完整说明？

这些场景通过后，才可以判断首发管理设计基本完善。本次复核仅形成上述清单，未改动管理台页面、真实权限或服务端实现。
